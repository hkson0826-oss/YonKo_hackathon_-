## 전략과 우리 v2의 차이

팀원 전략은 새 버전이 아니지만, 공개된 설명으로 의도와 한계를 더 정확히 확인할 수 있다. [팀원 전략 원문](../records/teammates/round2/team-7148f5d/bots/delineate_v1/STRATEGY.md), [Python 소스](../records/teammates/round2/team-7148f5d/bots/delineate_v1/main.py), [우리 C++ 소스](../submissions/tuned/main.cpp).

| 항목 | 팀원 Python v1 | 우리 C++ v2 |
|---|---|---|
| 의사결정 | 하나의 거리·가치 기반 배정 정책 | 4개 정책의 내 행동×상대 행동 행렬, 최대 4턴 시뮬레이션 |
| F 배정 | 거리−가치+중복 18+주둔 W 패널티 최소화 | 자체 3개 정책과 팀원 배정 정책의 이식본을 후보로 사용 |
| W 배정 | 목표 3칸 이내 적 W+1을 요구 병력으로 추정 | 정책별 배정 후 합법적인 양측 공동 행동을 시뮬레이션 |
| 경제 가치 | HALL·첫 ENG 5, HOSPITAL 4 등의 기능 보너스; 마지막 60턴 감쇠 | 정책 보너스 외 평가 함수에 ENG 110, 회관 수입 차×35, 병력 가치 차×1.3 등 적용 |
| 위험 회피 | 적 W의 한 턴 도달 상한과 아군 도착 예정 W 비교 | 정책 수준 위험 지도와 제한된 상대 후보의 탐색을 함께 사용 |
| TELE·종반 | TELE 미사용; 거리와 남은 턴으로 목표 제한 | 자체 정책은 TELE 후보 사용; 탐색 종료 상태에 공식 점수·누적 점령·병력 판정 적용 |
| 숨은 점수 | 대칭 추론, 불명확하면 지역 평균 | 현재도 대칭 추론·지역 평균이며 정확한 신념 분포는 미구현 |

팀원 방식의 장점은 임무 중복 비용과 요구 병력을 명시해서 F 분산과 W 집중을 따로 다룬다는 점이다. 전체 행동 탐색을 하지 않아 설계가 단순하며, Python 원본이 C++ 이식본과 별도로 있어 구현 차이를 드러내는 상대가 된다.

한계도 그대로 남는다. 매 턴 목표를 다시 배정하므로 임무가 흔들릴 수 있고, 적의 도달 상한은 실제 공동 행동 예측이 아니어서 F가 정체할 수 있다. 근처 적 W를 여러 목표에서 중복 수요로 셀 수 있으며, 위험 지도는 TELE 위협을 포함하지 않는다. 점령 예약은 생산 전 F 근접 여부에 기반한 근사치다. 이 내용은 소스에서 확인한 설계 제약이며 이번 공식 패배의 원인으로 확정한 것은 아니다.

우리 v2는 `assignment_policy`에 팀원 커밋 출처를 명시하고 이미 이 정책을 일부 채택했다. 이동·배정 동률 처리 등이 완전히 같다고 보장하지 않는다. 4×4 탐색 역시 열거하지 않은 상대 전술에는 안전성을 보장하지 않는다. 따라서 Python 원본을 상대 집단에서 제거하거나, C++ 이식본을 완전히 독립적인 새 상대라고 세지 않는다.

## 성능 주장 검토

팀원 [개발 기록](../records/teammates/round2/team-7148f5d/docs/development_log.md)은 2026-09-27에 이전 작업을 소급 정리했다고 명시한다. 새 전략 구현이나 새 실험의 증거가 아니다.

팀원 [결과 JSON](../records/teammates/round2/team-7148f5d/test-results/delineate-v1/results.json)의 수치는 문서와 일치한다.

- 시드 0·1, 제공 lv1·lv2, 양 진영: 8전 8승, 29~43턴 종료.
- 첫 판단 최대 약 13.442ms, 이후 판단 최대 약 5.107ms.
- 8개 경기의 독립 프로세스 입력·출력 일치 여부는 모두 참으로 기록됐다.
- **시간은 판단 함수 실행 시간**이다. Windows 별도 프로세스 러너 오류 때문에 InProcessBot으로 대전했으며, 서버의 프로세스 기동·턴별 통신·격리 제한까지 검증한 값이 아니다.

이번에는 해당 기록을 읽고 수치만 대조했으며 8경기를 다시 실행하지 않았다. 소스가 기존 상대와 같으므로 우리의 실제 프로세스 대전 기록도 계속 유효한 비교 자료다.

| 우리 v1 대 팀원 Python v1, 1000~1019 양 진영 | 25승 15패 | v1의 약점 발견 |
| 우리 v2 대 같은 Python v1, 같은 개발 맵 | 38승 2패 | 후보 선택에 사용 |
| 우리 v2 대 같은 Python v1, 3000~3019 양 진영 | 38승 2패 | v2 소스 고정 후 검증 |

[v1 대전 기록](05-팀원봇대전.md), [v2 검증 기록](06-v2튜닝결과.md). 위 검증 시드를 앞으로 수정에 사용하면 다시 미사용 검증 집합으로 부르지 않는다. 동일 코드의 이름을 바꿔 재대전해도 상대 다양성이 늘어나지 않는다.

## 규칙 문서 대조

팀원 [rule.md](../records/teammates/round2/team-7148f5d/docs/rule.md)는 배포 [공식 규칙서](../yk-development-tools/docs/rulebook.md)의 재정리다. 핵심 수치·단계·판정을 대조한 범위에서는 변경을 발견하지 못했다.

| 확인한 항목 | 대조 결과 |
|---|---|
| 15×15, 160턴, F/W/S 5/3/2 | 일치 |
| 생산→동시 이동→전투→효과→수입→점령→공개→승리 | 일치 |
| 새 병력 즉시 이동, 도착 병력 재이동 금지 | 일치 |
| W 상쇄 후 F 제거, 소유 건물 F 사망 시 중립화 | 일치 |
| 적 건물 2단계 점령, 전투 중립화 후 같은 턴 탈환 | 일치 |
| 점령 순서와 정보 공개, 대칭 점수 추론 | 일치 |
| 점수→누적 점령→병력 환산의 최종 판정 | 일치 |
| 300ms/첫 턴 3000ms, CPU 전용, 임의 데이터·학습 가중치·실행 파일 금지 | 일치 |

팀원 문서가 추가로 명시한 신촌/중앙/안암의 x 범위 0~4/5~9/10~14도 `config/balance.json`과 일치한다. 새 게임 규칙으로 엔진이나 봇을 바꿀 필요는 없다. 메모리·정확한 언어 버전·출력 제한은 팀원 요약만으로 판단하지 않고 [배포 제한](../yk-development-tools/bots/dist/starter/limits.json)을 유지한다.

[instructure.md](../records/teammates/round2/team-7148f5d/docs/instructure.md)는 기초 강의 요약이며 게임 수치의 권위 있는 근거가 아니다. 예컨대 정찰의 “맵·상대 정보 파악”이라는 일반적인 설명은 실제 게임에서 지형·병력·자원이 이미 공개된다는 규칙에 맞춰 읽어야 한다. 실제로 숨은 것은 건물 점수다.

## 운영·보고서 규칙 확인

팀원 [operation_rule.md](../records/teammates/round2/team-7148f5d/docs/operation_rule.md)는 다음을 설명한다. 이 파일 자체에는 원문 URL과 수집 시각이 없어 처음에는 보류했고, 이후 공식 웹 대조에서 최종 대진·순위 기준·마감·보고서 배점·중급 수료 조건을 확인했다. [공식 확인 기록](10-사이트운영과보정점수.md).

| 확인된 운영 규칙 | 적용할 내용 |
|---|---|
| 리더보드는 참고용이며 최종 순위에 직접 반영하지 않음 | 현 리더보드에만 맞춘 튜닝 방지 |
| 최종은 등록 진영 유지, 반대 진영 모든 팀과 1경기씩 | Y 성능을 실제 주 지표로 보고 K를 대칭·일반화 검사로 활용 |
| 승점률→승률→상대 승점률을 이용한 동률 기준 | UI 보정 점수와 같은 산식인지 공식 표에서 확인 |
| 10/1 23:00 파일 제출, 23:59 선택·보고서 마감 | 서로 다른 세 마감(리더보드/파일/선택)을 실행 계획에 반영 |
| 보고서 개발 과정 30점, LLM 모델·프롬프트·목적 기재 | 실제 변경 근거·실험·실패와 AI 활용 범위 보존 |

공식 확인된 세 번째 동률 기준은 `(이긴 상대들의 승점률 합 + 비긴 상대들의 승점률 합×0.5) / 자기 경기 수`다. 이것과 개발 리더보드의 “보정 점수”가 같은 산식인지는 아직 확인하지 못했다. 두 지표를 혼용하거나 확인되지 않은 산식을 튜닝 목적함수로 사용하지 않는다. 중급 모의 전투 10맵 중 6승 수료 조건과 보고서 배점 15/20/20/30/5/10도 공식 웹에서 확인했다.

팀원의 [LLM 기록](../records/teammates/round2/team-7148f5d/docs/llm_usage_log.md)은 팀원 작업의 사용자 프롬프트와 활용 범위다. 이를 우리 대화의 프롬프트·실험으로 옮겨 적지 않는다. 정확한 모델 세부 버전을 확인하지 못했다고 표시한 점도 유지한다.
