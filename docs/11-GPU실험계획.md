# RTX 3090 8개를 활용하는 단계별 실험 계획

작성일: 2026-09-27. **원격 GPU 서버에서 학습을 시작하지 않았다.** 사용자가 사용할 수 있다고 확인한 자원은 RTX 3090 최대 8개이며, 장치별 실제 VRAM·서버 CPU/RAM·접속 방식·사용 가능 시간은 아직 확인되지 않았다. 아래 시간·경기 수는 실행 전 검토할 초기 제안 예산이다.

목표는 GPU 사용률 자체가 아니라 **현재 제출 C++ 봇의 약점을 발견하고, 제출 가능한 수정으로 연결하는 것**이다. 공식 서버는 CPU 실행이며 학습 가중치·임의 데이터·실행 파일 제출이 금지된다. 연구 모델을 소스 배열이나 룩업 테이블로 숨겨 제출하는 경로는 사용하지 않는다. [공식 규칙](https://yonsei-vs-korea-hackathon.kr/rules), [방법별 근거·한계](08-다양한접근과근거.md)

다음 CPU 측정은 고정 소스 스냅샷으로 병렬도 1/2/4/8, 각 64경기를 반복하고 실행 순서를 바꾼다. 동일 상태의 C++ 정책 계산, Python 엔진 전이, 프로세스 I/O, 결과 저장 시간을 나눠 측정한다. GPU 환경을 새로 구현하기 전에 이 중 실제 병목부터 확인한다.

## 2. 첫 연구용 모델의 입력

학습 상태는 엔진 내부 `GameState`에서 직접 가져오지 않고, 해당 진영의 **실제 프로토콜 입력을 직렬화한 결과**에서 만든다. 공개되지 않은 건물 점수는 별도 알려짐 마스크와 함께 표현한다. `-1`을 실제 점수로 학습시키거나 원본 리플레이의 숨은 값을 채워 넣지 않는다. Actor와 가치 추정기 모두 같은 합법 정보만 사용한다.

| 표현 | 포함할 정보 |
|---|---|
| 15×15 격자 | 통행 가능·지형·양 본진, 내/상대 F·W·S 수, 건물 종류·소유권·점령 단계 |
| 건물별 표 | 위치·종류·공개 점수·알려짐 마스크, 합법 정보로 추론한 점수 범위, 현재 목표까지 거리 |
| 전역 벡터 | 현재 턴·남은 턴, 내/상대 공개 자원, 내 진영 |
| 합법 이력 | 이전에 관측한 건물 소유권, 점수 공개, 자기 임무·이전 행동, 프로토콜로 확인 가능한 소유 기간 |

병력 수는 로그 변환과 정규화를 하더라도 큰 병력 차이를 전부 같은 값으로 잘라 버리지 않는다. 원본 정수 관측도 재현 로그에 남긴다. 점수 범위나 거리 같은 파생 특징은 C++ 구현에서도 계산 가능한지 확인한다.

한 경기의 여러 턴을 훈련·검증에 나눠 넣지 않는다. 같은 맵의 Y/K 경기와 같은 지도에서 얻은 관련 리플레이는 같은 데이터 분할에 넣는다. 방향 정규화와 대칭 증강은 규칙·건물 종류·진영 특수 처리가 보존되는지 검증한 뒤 적용한다.

## 3. 첫 행동 공간과 학습 단계

처음부터 모든 칸·병종·수량의 명령 조합을 신경망으로 직접 출력하면 불법 명령과 호위 불일치가 많아질 수 있다. 먼저 기존 C++ 후보 생성기를 재사용해 학습 파이프라인을 검증하고, 다음에 실제 새 전술을 표현할 수 있도록 넓힌다.

| 단계 | 모델이 고르는 것 | 명령 생성·검사 |
|---|---|---|
| A: 선택기 대조 | 현재 v2의 4개 전체 정책 중 하나 | 고정 C++ 생성기로 전체 명령 구성. 임의 조합 없음 |
| B: 역할 계획 | 경제 유지·안전 확장·호위 돌파·병원 압박·F 차단·종반 중립화 중 계획, 중요 목표 최대 2~4개 | 역할 배정기가 F/W·생산 예산·도착 시각을 함께 결정 |
| C: 국소 수정 | 중요한 부대의 대기·철수·합류·분할 문턱 중 하나 | 인원 중복 사용, TELE 횟수, 생산 위치·비용, 점령 비용을 다시 검사 |

A는 학습형 선택기와 현재 4×4 탐색의 비교다. 같은 4개 정책만 고르므로 새로운 행동 생성 능력은 제한된다. A가 약점을 못 찾는다고 GPU 연구 전체가 무용하다고 단정하지 않으며, A의 성공을 새 전술 발견으로 과장하지도 않는다. B/C의 역할·목표 후보와 마스크는 코드를 고정하고 버전별로 관리한다.

첫 모델은 작은 격자 인코더와 건물·전역 벡터를 결합한 정책/가치 헤드로 제한한다. 예시 상한은 50만 파라미터, 3개 합성곱 층·32채널 또는 작은 MLP 대조군이다. 이는 미검증 초기 설계이며 작은 문제에 불필요한 대형 모델을 쓰지 않기 위한 상한이다. 숨은 정보 때문에 순환 모델이 필요하다는 근거가 생기기 전에는 합법 이력 특징으로 시작한다.

1. 고정 CPU 봇에서 모은 합법 관측·행동으로 선택기 또는 역할 결정기를 모방한다. 생성기에서 같은 명령이 나온 여러 정책은 모호한 정답으로 표시하거나 공동 확률을 처리한다.
2. 고정 상대 집단에서 정책경사 방식의 짧은 온라인 학습을 대조한다. 학습 알고리즘·배치 크기·할인율·난수는 실험 설정에 고정한다.
3. 연구 정책이 발견한 실패를 원본 상태·관측·행동과 함께 저장한다. C++ 수정은 별도 후보에서 진행한다.

모방학습 데이터만 사용하는 단계와 환경을 새로 실행하는 강화학습 단계를 구분한다. 모방 손실 감소는 승률 개선을 뜻하지 않는다.

## 4. 보상과 고정 상대 집단

학습의 기본 종료 보상은 승 +1, 무 0, 패 -1로 시작한다. 이 값은 학습 편의를 위한 부호이며 공식 승점 산식을 대체하지 않는다. 후보 채택은 별도로 계산한 **실제 Y 진영 승점률**과 상대별 성적에 따른다. 개발 보정 점수의 미공개 산식을 만들어 학습 보상으로 쓰지 않는다.

경제 거점·생존 F·병력·점수 변화는 진단 지표로 먼저 기록한다. 중간 보상이 필요하면 거점 잠깐 점령 후 상실을 반복하며 보상만 얻는지 검사하고, 보조항 전체의 경기 기여를 제한해 종료 보상을 압도하지 않게 한다. `종료 보상만` 대조군을 남기고 최종 평가에서는 보조 보상을 끈 실제 게임 성적을 사용한다. 정규화·할인·종료 시 잠재값 처리가 바뀌면 보상의 정책 불변성이 자동 보장된다고 말하지 않는다.

상대 집단은 v1, v2, 팀원 원본, 코드 구조가 다른 독립 공략형으로 시작한다. 독립 공략형은 구현·검증된 버전만 등록한다. 연구 시작 시 상대 소스·ZIP·실행 파일 해시와 샘플링 분포를 고정하고, 진행 중 바뀐 상대는 다음 run에서 사용한다.

초기 분포 제안은 현재 제출물 40%, 팀원 25%, 과거 강한 후보 15%, 독립 공략형 20%다. 실제로 마지막 그룹이 준비되지 않았다면 해당 비중은 구현된 그룹에 재분배하고 설정에 명시한다. 이후 성과가 있으면 어려운 상대 비중을 늘리되 어느 그룹도 관찰되지 않는 상태로 없애지 않는다. 이 비율은 학습 제안이며 최종 실제 대진 분포가 아니다.

## 5. 데이터 분할과 비교 단위

맵 seed, 정책 seed, 학습 초기화 seed를 따로 기록한다. 아래 집합 크기는 첫 파일럿 제안이다.

| 집합 | 용도 | 제안 크기·접근 |
|---|---|---|
| 개발 | 학습·튜닝·실패 원인 분석 | 실행 전 manifest로 정한 최소 256개 새 맵 |
| 후보 선택 | 학습 중 checkpoint 선택 | 개발과 다른 16개 맵 × 4개 고정 상대 × Y/K = 128경기 |
| 최종 검증 | 선정 후보의 외부 확인 | 별도 32개 맵 × 4개 상대 × Y/K = 256경기, 후보 선택 후 1회 |
| 공식 실패 상태 | 회귀·반례 검사 | 학습에 활용하면 개발 자료로 표시. 최종 검증의 독립 증거로 재사용하지 않음 |

기존 1000대·2000대·3000대·4000대 seed 범위를 단순히 보류라고 가정하지 않는다. 모든 과거 기록을 조회해 중복 여부를 확인한 manifest를 생성한다. 미공개 검증 집합을 AI 수정 프롬프트에 계속 보여주지 않는다. 검증 결과를 읽고 수정하면 해당 집합은 개발로 이동하고 새 검증 맵이 필요하다.

각 비교는 맵 단위로 Y/K를 묶고 동일 상대와 동일 정책 난수 묶음을 사용한다. Y 성적을 주표에, K와 양 진영 평균을 진단표에 둔다. 불확실성은 맵 묶음 bootstrap 등으로 보고하고, 반복된 같은 맵·정책 게임을 독립 표본 수로 부풀리지 않는다.

## 6. 1개 GPU의 첫 실행 예산

서버 접근·장비·사용 가능 시간이 확인된 뒤 아래 순서로 실행한다. 사전에 정한 한도 중 먼저 도달한 곳에서 종료한다.

| 단계 | 제안 예산 | 완료 조건 |
|---|---|---|
| 입력·명령 검증 | 32개 맵의 상태와 무작위 합법 명령 | 합법 관측 누출 0, 엔진 전이 대조 불일치 0, 명령 검증 오류 0 |
| 데이터 수집 | 고정 CPU 봇 512경기 또는 CPU 벽시계 30분 | 모든 경기 요약·오류 저장, 학습 입력 스키마 검증 |
| 배치 추론·학습 처리량 | GPU 1개, 환경 수 1/4/8/16, 각 3분 측정 | 프레임/초와 배치 지연·VRAM·CPU 사용률·GPU 대기 비중 측정 |
| 선택기 모방 | 최대 3 epoch 또는 GPU 벽시계 30분 | 관측 마스크·재현·checkpoint 저장 확인. 승률과 별도 평가 |
| 고정 집단 단기 학습 | 최대 4,096경기 또는 2 GPU시간 | 15분 간격 요약·checkpoint, 512경기마다 후보 선택 검사 |
| C++ 연결 검사 | 유망 반례 최대 10개 | 서로 다른 맵의 실패 전술, 규칙상 합법 대체 행동, 별도 C++ 후보 계획 |

첫 장치 파일럿은 처리량 측정을 포함해 **최대 약 3 GPU시간의 제안**이다. 후보 선택용 CPU 대전은 별도 자원으로 기록한다. 이 예산의 학습으로 강한 정책이 나온다는 보장은 없으며, 우선 목적은 파이프라인의 효용과 병목 판단이다.

연구용 GPU 정책은 배치 추론 때문에 300ms 제출 제한과 다른 스케줄을 사용할 수 있다. 학습용 환경의 제한과 비교용 환경의 제한을 로그에 명시한다. 고정 C++ 상대가 CPU 과부하로 시간 초과해서 생긴 승리는 전략 성과로 인정하지 않는다. 실제 제출 후보 검증은 공식에 가까운 CPU·버전·턴 제한에서 따로 수행한다.

## 7. 1 → 2 → 4 → 8개 확대 조건

후속 검토에서 계열별 GPU 2개 고정 배분을 **공용 작업 큐·동적 배분**으로 수정했다. 후보 수와 GPU 수를 분리하고, 한 장의 동시 학습 수와 배치 추론을 먼저 측정한다. 상세 설계와 추가 논문 근거는 [GPU 자원 배분 보완](13-GPU자원배분보완.md)을 따른다.

아래 숫자는 처음 정한 운영 기준이며 보편적인 최적 기준이 아니다. 변경하면 이전 결과를 보존하고 이유를 남긴다.

| 확대 | 통과 조건 | 불통과 시 |
|---|---|---|
| 1 → 2 | 전이·관측 검증 통과, 파일럿 중 데이터 손상·수치 발산·OOM 없음, CPU 기준보다 유용한 새 실패 또는 추가 학습 가치 확인 | 데이터/행동 공간/상대 집단부터 수정 |
| 2 → 4 | 같은 작업 조건을 3회 측정했을 때 바로 전 단계인 2개 대비 총 유효 처리량 1.5배 이상, 재개 가능, CPU 대기·검증 지연 관리 가능 | CPU 엔진·I/O·배치 공급 병목 개선. GPU 추가 보류 |
| 4 → 8 | 바로 전 단계인 4개 대비 1.5배 이상 총 유효 처리량, 추가 정책들이 다른 패배 유형 발견, 저장·평가 큐 감당 가능 | 중복 정책 감축, 상대 다양성 수정, 남는 GPU 미사용 |

GPU 평균 이용률이 낮으면 배치 추론·데이터 공급을 확인한다. 일정 비율의 이용률만 억지로 맞추기 위해 의미 없는 계산을 늘리지 않는다. 높은 GPU 이용률이라도 새 반례나 실제 C++ 개선이 없으면 확대 근거가 약하다.

아래는 기존에 제시한 **전략 계열의 예시**다. 장치 2개씩을 계속 전용 배정하는 운영안은 채택하지 않는다. 각 계열은 공용 큐에 여러 설정·난수 후보를 넣고 측정된 자원 요구와 성과에 따라 실행한다. 한 대형 모델의 8개 장치 분산 학습보다 낫다는 실측 결과는 아직 없다.

| 후보 계열 | 연구 목표 |
|---|---|
| 일반형 | 전체 고정 집단에 대한 동일 설정, 서로 다른 학습 seed |
| 경제 공략형 | 현재 C++의 경제 거점 수비·호위를 공격하는 연구 상대 |
| 종반 공략형 | 종반 중립화·다방향 F 확장 상대 |
| 연구 대조형 | 행동 표현 A/B 또는 보조 보상 유무 같은 한 요소의 대조 |

최종 검증을 연구 목표나 학습 보상으로 전달하지 않는다. 장치별 체크포인트 경쟁에서 가장 좋은 점수만 골라 보고하지 않고 전체 run 수·실패·선택 비용을 기록한다. CPU 검증 전용 자원을 남겨 학습 부하가 후보 응답 시간에 섞이지 않도록 한다.

| 지연 | 환경 전이, 정책 배치 대기, 추론, 역전파, IPC, 리플레이 저장의 각각 p50/p95/p99/max |

예시로 `nvidia-smi`의 주기적 CSV와 OS 프로세스 계측을 이용하되, 설치 버전과 명령을 manifest에 남긴다. GPU 정보에서 자격 증명이나 원격 접속 비밀을 결과 파일로 복사하지 않는다.

## 9. CPU 탐색과 같은 예산의 대조

GPU 실험과 별도로 **같은 벽시계 시간·동일 CPU 코어 할당**의 C++ 파라미터 탐색을 진행한다. GPU 사용량은 추가 자원으로 별도 보고하므로 두 실험을 동일 비용이라고 표현하지 않는다. 둘 다 동일한 고정 상대·후보 선택/검증 묶음을 사용한다.

대조는 `현재 v2`, `CPU 무작위/NTBEA 등 설정 탐색`, `GPU 연구 상대에서 얻은 명시적 C++ 수정`이다. GPU 정책 자체의 승률과 제출 후보의 승률을 표에서 분리한다. 후보 수, 총 환경 전이, CPU 코어시간, GPU시간, 에너지 측정 가능 여부를 함께 남긴다. 시간만 길게 써서 얻은 향상과 알고리즘 효율을 구분한다.

CPU 탐색이 같은 시간에 더 많은 독립 반례와 더 강한 합법 제출 후보를 만들면 CPU 경로를 우선한다. 작은 격자·가벼운 모델·프로세스 기반 환경에서는 GPU 8개가 충분히 공급받지 못할 가능성이 있으나, 이는 측정으로 판단한다.

## 10. 중단·재개와 기록 구조

다음은 즉시 중단 조건이다: 관측에 숨은 정보 포함, 공식 엔진과 전이 불일치, 깨진 checkpoint, 반복 NaN/OOM, 상대 프로세스 오류를 승리로 처리, 기록 없는 소스 변경. 원인을 고쳐 새 run ID로 재시작한다. 의도하지 않은 후보/상대 변경을 같은 run에 섞지 않는다.

성능 측면에서는 예산 한도 도달, 두 연속 평가 구간 동안 새 반례·후보 성능 변화 없음, 이미 알려진 한 맵 실패만 반복, 장치 증가에 따른 처리량 기준 불충족이면 해당 확대를 멈추고 결과를 보류한다. 작은 표본의 승률 정체만으로 알고리즘이 영원히 불가능하다고 결론 내리지 않는다.

```text
records/compute/<run-id>/
  manifest.json          # 코드·엔진·설정·상대 해시, 장비, 명령, 예산, 시작/끝/상태
  hardware.json          # 장치·CPU/RAM·라이브러리와 실제 자원 할당
  metrics.jsonl          # 처리량·지연·학습·자원 지표
  games.jsonl            # 전 경기 결과와 오류
  splits.json            # 맵·정책·학습 seed와 데이터 분할
  checkpoints.json       # 체크포인트 경로·해시·연결된 전이 수
  findings.json          # 새 실패·가설·채택/보류 이유
records/replays/<run-id>/
  ...                    # 패배·무승부, 전략별 대표 승리
<local-artifact-store>/<run-id>/
  snapshots/             # 불변 코드·설정 스냅샷
  checkpoints/           # 모델·optimizer·RNG·학습 카운터, Git/제출 제외
  datasets/              # 합법 관측 데이터, 스키마·샤드 해시
```

체크포인트는 임시 경로에 쓴 뒤 해시·읽기 검사를 거쳐 교체한다. 중단 위치, 환경 seed, 정책 난수, optimizer 상태, 버퍼 포함 여부를 기록한다. 원자적 전체 재개가 불가능하면 새 하위 run으로 시작하고 동일 실행의 연속이라고 표현하지 않는다. 비동기 환경은 checkpoint 시점에 진행 중이던 경기의 중단·완료 처리 방식을 명시한다.

연구 코드는 `jisang`의 고정 커밋 또는 소스 해시 스냅샷을 사용한다. GPU checkpoint·대형 데이터셋·가상환경은 Git과 제출 ZIP에 넣지 않는다. `main`에는 검증된 C++ 소스/ZIP, 필요한 요약과 재현 설정만 선별 공유한다.

## 11. 실제 제출 개선으로 인정하는 조건

1. 연구 모델이 v2를 공략한 사례를 서로 다른 맵에서 찾고 당시 합법 관측·행동·턴 증거를 남긴다.
2. 상대 행동을 고정한 한 턴 반사실과 상대가 계속 반응하는 전체 경기를 구분한다.
3. 발견 전술에 대응하는 **명시적 C++ 게임 로직**을 별도 후보로 구현한다. 학습 가중치나 자동 증류 테이블을 옮기지 않는다.
4. 같은 개발 실패와 새로운 맵·상대 집단에서 평가하고, Y 승점률 개선·주요 상대군 회귀·종반·오류를 확인한다.
5. 공식에 가까운 C++20 GCC 12.2.0 CPU 환경에서 응답 시간·메모리·출력·제출 ZIP 검사를 통과한다.

이 조건을 통과하기 전에는 “GPU로 더 강한 제출 봇을 만들었다”고 보고하지 않는다. 현재 완료된 일은 환경 확인·짧은 CPU 처리량 검사·연구 설계이며, 원격 접속 정보가 제공되기 전까지 서버 GPU 훈련은 미실행 상태다.
