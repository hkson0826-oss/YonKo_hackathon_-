# GPU 8개: 고정 분할에서 공용 작업 큐로

2026-09-27. 이전의 ‘네 계열에 2개씩’은 비교할 전략을 설명한 예시였고 자원 최적화 계획으로는 부족했다. **8개 GPU는 여러 연구 후보가 공유하는 자원으로 운영한다. 후보 수·동시 실행 수·한 후보의 GPU 수는 서로 다른 값이다.** 아래는 추가 연구를 반영한 미실행 설계이며, 이 서버에서 최적이라고 실측한 배치가 아니다.

## 1. 무엇이 달라지는가

| 이전 설명의 한계 | 수정안 |
|---|---|
| GPU 한 장 또는 두 장을 전략에 고정 | 공용 큐가 빈 장치에 작업 배정. 처리량이 좋아지는 경우 한 장에 여러 작은 학습기 배치 |
| 사실상 8개 모델에만 자원을 묶음 | 수십 개 설정·역할·학습 seed 후보를 큐에 두고 측정된 동시 실행 수만 활성화 |
| 초기 배분을 끝까지 유지 | 최소 학습량 이후 비교해 유망 후보·새 반례·독립 재검증에 다음 구간 배정 |
| GPU 수를 늘리면 경기도 빨라질 것으로 기대 | CPU 환경·추론·학습·저장·검증을 분리해 실제 병목을 먼저 개선 |
| 상위 승률 모델만 계속 복제 | 과거 강한 상대와 서로 다른 공략 계열을 보존. 같은 실패의 반복에는 추가 자원 축소 |

한 GPU에 여러 모델을 올리는 가능성은 실제 연구에도 있다. Sample Factory는 CPU 환경 실행, 배치 정책 추론, 학습을 분리하며, 논문 실험에서 GPU 하나에 복수 학습기와 정책 worker를 배치했다. 해당 게임·장비의 처리량을 이 게임이나 RTX 3090 성능으로 옮겨 쓰지는 않는다. [Sample Factory](https://arxiv.org/abs/2006.11751)

## 2. 경기 생성과 GPU 계산을 분리

흐름은 `CPU 경기 workers → 합법 관측 큐 → GPU 배치 추론 → 행동 반환 → CPU 전이`, 그리고 `완료한 궤적 → GPU 학습 → 버전이 붙은 정책 스냅샷`이다. 검증용 CPU는 학습 부하와 분리한다.

- 여러 경기의 **같은 정책·같은 버전** 요청을 묶어 추론한다. 정책이 다른 요청은 그룹을 나누며, 동일 구조라도 서로 다른 가중치를 일반 배치 하나로 자동 처리할 수 있다고 가정하지 않는다.
- 배치 최대 크기와 최대 대기 시간을 함께 둔다. 배치가 너무 작으면 GPU 호출 비용이 커지고, 너무 크면 경기 대기·이전 정책 데이터가 늘어난다. 정책 버전 지연과 큐 길이에 상한을 둔다.
- learner와 추론 프로세스의 장치 공유 여부도 측정 대상이다. 여러 학습 프로세스를 무조건 늘리면 CUDA context·메모리·대역폭·스케줄링 경합으로 총 처리량이 줄 수 있다.
- 비동기 학습은 오래된 행동 정책으로 수집한 데이터를 처리할 수 있는 학습법·보정이 필요하다. 기존 동기 PPO를 그대로 무제한 큐에 붙이지 않는다. 행동 당시 정책 버전·확률과 데이터 나이를 기록한다.
- GPU가 여러 서버에 나뉘었다면 관측·궤적·모델 전송 비용을 측정한다. 가능하면 경기 worker·추론·학습을 같은 노드에서 처리하고 노드 사이에는 checkpoint와 평가 결과를 우선 공유한다.

이 분리는 Sample Factory의 설계에서 가져온 원리다. 해당 논문의 환경 worker 수나 FPS를 설정값으로 그대로 가져오지 않는다. 현재 로컬 측정은 **CPU 4경기 반복 검사**뿐이며 GPU 공급 능력은 측정하지 않았다. [측정 기록](../records/compute/round2/runtime-profile.json)

## 3. 한 장의 처리량부터 측정

먼저 장치별 실제 VRAM, 서버 CPU 코어·RAM, GPU 연결 구조, 노드 수를 조회한다. 다음 값은 측정할 후보이며 권장 정답이나 이미 가능한 동시 실행 수가 아니다.

| 조절값 | 첫 비교 후보 | 선택 기준 |
|---|---|---|
| GPU당 활성 학습 작업 | 1 / 2 / 4 | 전체 유효 전이·학습 처리량, 작업별 진도, VRAM, 정책 지연 |
| CPU 환경 worker | 가용 물리 코어 일부부터 단계 증가 | 전이·상대 계산·IPC 분해 시간, 검증 CPU 여유 |
| worker당 환경 수 | 1 / 4 / 16, 필요할 때 확대 | GPU 대기 감소가 경기 지연 증가보다 유리한지 |
| 추론 batch | 32 / 128 / 512와 짧은 대기 상한 | 실제 도착 요청에 맞는 크기. 최대 batch까지 무조건 대기하지 않음 |
| 정책 갱신·학습 batch | 보수적인 초기값부터 단일 요소 비교 | 새 데이터 공급량·학습 안정성·정책 버전 지연 |

예컨대 8개 장치에서 각 2개 작업이 더 효율적이라고 **측정된 경우에만** 16개 동시 작업을 쓸 수 있다. 이는 현재 용량 예측이 아니다. 32개 후보 큐가 있어도 실제 동시 실행은 4개, 8개 또는 16개가 될 수 있다.

학습기 하나의 계산이 실제 병목이고 2개 장치 학습이 같은 품질에 더 빨리 도달하면 그 후보에 여러 GPU를 배정하는 방법도 비교한다. 작은 모델에서는 통신·동기화 비용이 커질 수 있으므로 처음부터 8개 전체를 한 모델에 묶지 않는다.

## 4. 후보를 넓게 찾고, 성과에 따라 다음 예산 배정

첫 모집단의 예시는 **4개 전략 계열 × 4개 설정 × 학습 seed 2개 = 32개 연구 후보**다. 모든 후보를 즉시 동시에 실행한다는 뜻은 아니다. 선택기·역할 계획·국소 행동 표현 등 아직 구현하지 않은 후보는 준비된 뒤 큐에 넣는다. CPU 규칙 기반 배정·탐색·NTBEA 후보는 별도의 CPU 큐에서 평가한다.

운영 순서는 다음과 같다.

1. 계열마다 최소 환경 전이 예산과 공통 고정 상대 평가를 보장한다. 장비가 달라 진도가 다른 후보를 같은 벽시계 시점의 승률만으로 탈락시키지 않는다.
2. 같은 계열·학습량의 후보끼리 비교해 다음 예산 구간을 배정한다. 불확실성이 크면 추가 평가한다. 초기 성과가 느린 계열을 위한 긴 초기 예산 집합도 남긴다.
3. 좋은 후보는 더 학습하거나 독립 seed로 재현한다. 약한 후보는 정지·보관하고 새 설정을 시작한다. 비슷한 구조의 학습기끼리는 PBT식 checkpoint 복제·설정 변경도 별도 대조한다.
4. 변경은 checkpoint 경계에서 수행한다. 부모 run·소스·입출력 schema·정책 버전·변경 이유를 기록한다. 구조·행동 의미가 다른 모델 사이에 가중치를 그대로 복사하지 않는다.
5. 과거 강한 봇과 새 공략형을 상대 저장소에 보존한다. 최신끼리의 승률만으로 다음 예산을 정하지 않는다. 최종 검증 집합은 배정기에 제공하지 않는다.

ASHA는 완료한 후보를 비동기적으로 비교·승급해 느린 실행을 기다리는 시간을 줄이는 근거다. PBT는 학습 중 유망한 checkpoint와 하이퍼파라미터를 이용해 다른 후보를 갱신하는 근거다. **두 방법을 모든 후보에 중복 적용하는 구현을 권하는 것은 아니다.** 처음에는 최소 예산을 둔 중지·재개 방식으로 시작하고, 같은 구조의 학습기가 안정화된 뒤 PBT를 비교한다. [ASHA](https://arxiv.org/abs/1810.05934), [PBT](https://arxiv.org/abs/1711.09846)

운영 시작 시 총 GPU시간의 예시 배분은 `유망 후보 확장 50% / 새 전략·공략 탐색 30% / 독립 seed 재검증 20%`다. 고정 장치 번호가 아니라 다음 실행 구간에 배정하는 예산의 비율이다. 이 값은 미검증 제안이며, 계열별 최소 예산과 장기 학습 후보를 위한 몫을 보장한 뒤 조절한다. CPU의 최종 검증 예산은 별도로 남긴다.

## 5. 승률 외에 새 실패의 가치도 평가

일반형은 고정 상대 집단에 대한 Y 승점률, 공략형은 현재 제출물에 대한 **새 맵의 재현 가능한 실패와 기존에 없던 전술**을 우선 평가한다. 서로 다른 목적의 후보를 각자의 shaping reward로 한 표에서 직접 순위 매기지 않는다. 공통 승점률과 계열별 목적을 분리한다.

동일 실패를 계속 반복하는 모델보다 새로운 경제 붕괴·F 경합·종반 역전 사례를 내는 모델에 연구 예산을 줄 수 있다. 재현 가능한 반례 수, 대응한 명시적 C++ 수정 수, 새 맵에서 검증된 성능 개선을 함께 남긴다. 한 후보의 평균 승률이 낮아도 독립적인 상성·실패 유형을 제공하면 보관한다.

AI는 완료 배치의 실패 위치·선택 행동·대체 행동·결과를 읽고 다음 후보의 코드·설정을 수정한다. 수정은 새 실행 ID로 시작한다. 같은 실행 중인 소스를 계속 바꾸거나 최종 검증 점수를 반복해서 수정 프롬프트에 공급하지 않는다.

## 6. CPU가 막히면 GPU에 무엇을 더 시킬 것인가

1. 현재 Python 엔진·스레드 러너·봇 subprocess·저장 시간부터 분해한다. CPU 프로세스 병렬화와 검증된 C++ 전이의 학습용 연결을 먼저 비교한다. 학습용 고속 runner와 실제 제출용 subprocess 검사는 구분한다.
2. 여전히 환경 전이가 지배적이고 반복 학습 총량이 크다면 GPU 배치 시뮬레이터를 후보로 둔다. 명령 순서·동시 이동·자원 절삭·순간이동·점령 단계·숨은 점수·종료 판정까지 공식 엔진 차등 검사 후 사용한다.
3. 구현 투자 회수도 계산한다. 남은 N개 전이, 기존 처리량 S0, 새 처리량 S1이라면, 구현·검증 시간 T가 `N/S0 - N/S1`보다 작을 때 시간상 이익이 있다. S1은 실제 파일럿으로 측정한다. 이 부등식만으로 전략적 이익을 보장하지는 않는다.
4. 실제 제출 가능한 개선으로 연결되지 않는 GPU 작업은 줄인다. 현 규정상 학습 가중치 제출은 금지이며, 연구 전술은 명시적인 C++ 로직과 독립 검증을 거쳐야 한다.

한 번에 ‘수백만 경기 가능’이라고 약속할 근거는 없다. 1→2→4→8개 확대는 **바로 전 단계**와 같은 작업 조건의 처리량·학습 품질·총 자원 시간을 비교한다. 두 배 장치에서 1.5배 처리량이라는 기준은 초기 운영 가정이며 최적성 기준이 아니다. GPU 사용률과 후보 수만 늘고 유효 전이·독립 반례·제출 성능이 늘지 않으면 병목이나 연구 방향을 바꾼다.

## 근거와 현재 완료 범위

- Sample Factory: CPU 환경·GPU 추론·learner 분리, 복수 learner/GPU, 배치·통신·정책 지연을 본문 확인.
- PBT: 최소 학습 후 성과 비교, checkpoint 복제, 하이퍼파라미터 변경을 본문 확인.
- ASHA: 최소/최대 자원, 비동기 승급·중지, 조기 잘못된 승급 가능성을 본문 확인.
- [Firecrawl 원문 근거](../records/research/gpu-allocation/README.md). 논문 결과를 이 대회에서 재현한 것은 아니다.

이번 수정은 운영 설계와 확대 기준 보완이다. 공용 스케줄러·GPU 학습기·배치 시뮬레이터는 아직 구현·실행하지 않았다. 원격 서버 접근·자원 확인 후 첫 파일럿이 필요하다.
