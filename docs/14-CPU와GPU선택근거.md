# 강한 C++ 후보를 빨리 찾기 위한 CPU·GPU 선택

2026-09-27. 목표는 **같은 시간에 더 강한 알고리즘 코드를 검증해 얻는 것**이다. GPU 이용률이나 실행 후보 수는 그 목표를 위한 보조 지표다. 현재 추천은 **CPU 전체 대전·후보 선별과 GPU의 큰 배치 계산을 함께 운영하는 구조**다. CPU가 모든 경우에 더 낫다거나 GPU 8개가 반드시 더 빠르다는 결론은 아직 없다. 실제 비교 결과는 [실행 측정 기록](15-CPU와GPU실측결과.md)에 연결한다.

## 이전 계획에서 바꾸는 점

[GPU 실험 계획](11-GPU실험계획.md)과 [자원 배분 보완](13-GPU자원배분보완.md)은 별도 신경망 상대를 학습시키는 연구까지 포함했다. 현재 우선 작업은 **규칙 기반 코드·파라미터 후보를 생성하고 많은 대전으로 비교하는 것**이다. 모델 학습기와 정책 추론 서버를 만드는 일은 이 작업의 선행 조건이 아니다. 신경망 연구를 영구 배제하는 결정도 아니다.

사용자가 제시한 ‘조금씩 다른 설정을 엄청 많이 계산하기’는 GPU에 적합할 수 있다. 다만 다음 세 작업의 비용과 증거를 구분해야 한다.

| 작업 | CPU에서 할 일 | GPU로 가져갈 후보 | 평가할 결과 |
|---|---|---|---|
| 다른 알고리즘 코드 비교 | 각 실행 파일로 공식 엔진 전체 대전 | 자주 쓰는 계산 구조가 정리된 뒤 계열별 커널 | 새 맵·상대에서 승점률, 오류, 응답 시간 |
| 같은 코드의 많은 설정 비교 | 설정 생성·후보 선별·전체 대전 | 같은 계산을 설정 × 상태 × 행동에 반복하는 큰 배치 | 전송 포함 처리량, 선택 후보의 실제 대전 결과 |
| 매우 많은 전체 경기 | 프로세스 병렬화, 필요하면 C++ 고속 러너 | 상태 전이·행동 결정 모두를 묶는 배치 시뮬레이터 | 공식 전이 일치, 완료 경기/초, 전체 투자 회수 |

GPU에 서로 다른 C++ 실행 파일을 그대로 넣어 실행하는 구조는 아니다. GPU용 공통 연산과 데이터 배치가 필요하다. 같은 알고리즘의 설정값을 배열로 바꾸는 쪽이 매번 구조가 달라지는 코드 전체를 이식하는 쪽보다 재사용하기 쉽다. 서로 다른 계열은 별도 배치·커널로 묶어 제어 흐름의 차이를 줄인다. 이 판단은 CUDA의 같은 warp 내 분기 비용과 전송 비용에서 나온 설계 추론이며, 이 게임에서 측정된 배속을 뜻하지 않는다. [NVIDIA CUDA Best Practices](https://docs.nvidia.com/cuda/cuda-c-best-practices-guide/index.html#control-flow-instructions)

## 먼저 바꿀 것은 후보 평가 방식

전체 조합을 같은 경기 수로 끝까지 평가하기보다 **동일 조건으로 조금 평가하고 유망 후보를 확대**한다. irace는 일반 알고리즘의 설정을 문제 인스턴스 집합에서 고르는 도구이며 대상 실행의 병렬화를 지원한다. SMAC3도 인스턴스 수를 평가 예산으로 쓰는 방식을 제공한다. 이것은 신경망을 전제로 하지 않는다. [irace 공식 안내](https://mlopez-ibanez.github.io/irace/), [SMAC3 인스턴스 예산](https://automl.github.io/SMAC3/latest/advanced_usage/2_multi_fidelity/)

적용 순서는 다음과 같다.

1. 코드 계열·파라미터의 의미와 범위를 고정한다. 공학관 가치, 수비 병력, 임무 유지, 종반 판단처럼 실제 패배와 연결된 설정부터 시작한다.
2. 후보들은 공통 맵·상대·정책 난수 조건에서 **끝까지 진행한 경기**로 비교한다. 평가 예산을 늘릴 때 맵·상대 조합 수를 늘린다. 160턴 경기를 앞부분만 실행하면 이번에 확인한 종반 패배를 놓친다.
3. 승점률이 좋거나 새로운 상성을 제공하는 후보에 다음 평가 예산을 배정한다. 평균이 낮아도 현재 제출물을 공략하는 독립적인 후보는 상대 집단에 남긴다.
4. 유망 설정 주변은 더 촘촘히 찾고, 다른 코드 계열의 탐색도 유지한다. irace식 반복 경쟁과 무작위 탐색을 같은 대전 예산으로 비교한 뒤 복잡한 선택기를 도입한다.
5. 후보 선택용 맵과 최종 검증 맵을 분리한다. 양 진영을 같은 맵 묶음으로 기록하고 Y 성적을 주 지표로 둔다. 최종 검증 결과를 보고 코드를 고치면 새 검증 집합을 사용한다.

이미 수집한 상태에서 GPU로 평가 함수를 수없이 다시 계산하는 것만으로 강한 설정을 확정할 수는 없다. 설정이 바뀌면 행동과 이후 경기 상태도 달라진다. **고정 상태의 계산은 처리량 검사·후보 사전검사이고, 최종 선택의 근거는 새로 진행한 대전**이다.

## CPU 병렬화가 의미하는 것

검토 시점의 `tests/benchmark.py`는 `ThreadPoolExecutor`에서 Python 엔진을 실행하고, 각 봇은 별도 subprocess로 구동한다. 따라서 ‘Python 스레드라서 봇 전체가 직렬’이라는 해석은 잘못이다. C++ 봇 계산은 이미 별도 프로세스이고, 부모 Python의 엔진·직렬화 부분에 GIL이 영향을 줄 수 있다.

일반적인 GIL 활성 CPython에서 `ProcessPoolExecutor`는 Python 경기 실행 자체를 별도 프로세스로 분산한다. 대신 프로세스 시작·직렬화·추가 메모리 비용이 있으므로 스레드보다 무조건 빠르지는 않다. 같은 경기 묶음으로 비교하고, 동시 봇 프로세스 수도 함께 계산한다. 작은 배치의 시작 비용을 포함한 전체 시간과 준비 후 처리량을 나눠 기록한다. [Python 공식 동시 실행 문서](https://docs.python.org/3/library/concurrent.futures.html#processpoolexecutor)

CPU 측에서 다음으로 큰 개선 후보는 검증된 C++ 전이를 이용해 경기와 정책을 한 프로세스에서 호출하는 고속 러너다. 문자열 프로토콜·프로세스 간 왕복을 줄일 가능성이 있지만, 공식 엔진과의 차등 검사·전역 상태 격리·난수 재현이 필요하다. 고속 탐색용 결과와 실제 제출 방식의 응답 시간 검사는 별도로 남긴다.

## GPU 파일럿과 확대 기준

GPU 파일럿은 먼저 현재 C++의 실제 계산 하나를 같은 입력·설정으로 실행한다. 단순한 행렬 곱의 배속으로 게임 성능을 추정하지 않는다. 비교는 ① 최적화된 CPU 계산 ② GPU 계산만 ③ 입력 생성·전송·결과 회수·동기화를 포함한 GPU 전체 경로로 나눈다. 최초 컴파일·준비 비용과 이후 반복 비용도 분리한다. NVIDIA도 대표 작업의 병목 분석, 장치 전송 최소화, 장치 내 데이터 재사용을 권한다. [NVIDIA 프로파일링·전송 지침](https://docs.nvidia.com/cuda/cuda-c-best-practices-guide/index.html#application-profiling)

큰 상태·설정 배열은 가능하면 GPU에 유지하고 결과는 요약해 가져온다. 경기마다 매 턴 작은 평가 한 번을 요청하면 대기·전송 비용이 계산 절약을 지울 수 있다. 배치 크기뿐 아니라 필요한 상태 공급량도 측정한다. 정책·맵·설정이 다르면 분기와 메모리 접근도 달라지므로 실제 다양한 상태로 측정한다.

**커널 가속과 전체 대전 가속은 다른 수치다.** 원래 전체 시간에서 옮길 부분의 비중을 `p`, 그 부분의 실측 가속을 `s`라고 하면, 전송 비용을 무시한 이상적 상한은 `1 / ((1-p) + p/s)`다. 실제 대전에서는 전송·준비·다른 병목 때문에 더 낮아질 수 있다. `p`를 측정하기 전에는 GPU 평가 함수가 빨라도 전체 경기 배속을 주장하지 않는다. [NVIDIA Amdahl 설명](https://docs.nvidia.com/cuda/cuda-c-best-practices-guide/index.html#strong-scaling-and-amdahl-s-law)

확대는 다음 조건으로 판단한다.

| 단계 | 통과해야 할 근거 |
|---|---|
| 계산 하나 이식 | 같은 정수 전이·종료 판정, 수치 오차 범위와 행동 선택 변화 확인. fast-math 사용 여부 고정 |
| GPU 전체 경로 사용 | CPU 계산보다 전송 포함 시간이 줄고, 실제 후보 탐색에서 해당 계산을 충분히 공급할 수 있음 |
| 전체 경기 이식 | 공식 엔진과 상태·행동·관측·종료 판정 차등 검사, 다양한 맵에서 실제 완료 경기/초 개선 |
| 1→2→4→8개 | 바로 전 장치 수와 같은 작업에서 처리량·장치시간·메모리·CPU 병목 비교. 독립 작업을 나누고 큰 동기화는 피함 |

남은 평가량이 `N`, 현재와 새 전체 처리량이 `S0`, `S1`이면 개발·검증 투자 시간 `T`가 `N/S0 - N/S1`보다 작은지 확인한다. 단위는 같은 유효 경기 또는 동일 작업량이어야 한다. 평가 함수 호출/초와 경기/초를 섞어 계산하지 않는다. 이는 계획을 판단하는 식이며 아직 확인하지 않은 GPU 속도를 대입하지 않는다.

## 현재 선택

**전체 대전과 후보 선택은 바로 확장할 수 있는 CPU 경로를 운영하고, GPU는 실제 반복 계산의 이식·배치 파일럿을 병행한다.** CPU 결과가 쌓이는 동안 GPU의 효과를 확인할 수 있다. GPU 파일럿이 통과하면 해당 계열의 설정 대량 평가로 확대하고, 전체 경기 이식은 병목과 투자 회수가 확인될 때 진행한다.

3090 8개를 한 후보에 묶기보다 독립적인 설정·맵 묶음으로 나누는 구성을 먼저 비교한다. 같은 계열을 함께 묶되 계열별 장치 수를 고정하지 않고 완료된 평가에 따라 다음 작업을 배정한다. 최종 기준은 **실제 새 맵 승점률을 개선한 후보 수와 그 후보를 찾는 데 든 시간**이다. 서버 CPU·RAM·실제 VRAM·연결 구조가 확인되기 전에는 코어 수나 GPU당 경기 수를 단정하지 않는다.

이 문서는 네 개의 공식 유지관리 문서와 현재 소스 구조에 따른 선택 근거다. 각 라이브러리를 설치·실행했거나 RTX 3090 서버에서 성능을 측정한 보고서는 아니다. [수집 출처와 짧은 원문 발췌](../records/research/compute-choice/sources.json), [현재 공식 실행 조건 확인 기록](10-사이트운영과보정점수.md)을 함께 보존한다.
