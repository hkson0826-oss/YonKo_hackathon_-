# 코드 후보 탐색: 실측 결과와 실행 방법

2026-09-27. **현재는 CPU 전체 대전 큐를 사용하고, 행동 생성 코드의 반복 계산을 줄이는 것이 우선이다.** AI는 패배 원인과 실험 결과를 읽고 새 코드를 만드는 데 사용한다. GPU는 같은 계산을 충분히 크게 묶을 수 있는 부분부터 검증한다. 별도 신경망 학습은 이 흐름의 필수 단계가 아니다.

개발에 쓰는 도구보다 최종 코드의 성능을 기준으로 선택한다는 사용자 설명을 반영했다. 이전 문서의 신경망 학습·추론 서버 설계는 선택적 연구안으로 남겼다. 방법별 출처와 선택 근거는 [14번 문서](14-CPU와GPU선택근거.md)에 있다.

## 1. v2에서 시간을 쓰는 곳

공식 5경기의 참가자 관측을 순서대로 입력해 v2의 판단 483회를 측정했다. 시간 계측을 추가하기 전후 출력 명령의 해시는 전부 같았고, 내부 160ms 제한에 따른 기본 정책 대체는 0회였다.

| 구간 | 누적 시간 | 판단 전체에서 비중 |
|---|---:|---:|
| 행동 후보 생성 `policy` | 6.329초 | 91.64% |
| 상태 전이 `advance` | 0.276초 | 3.99% |
| 점수 계산 `evaluation` | 0.253초 | 3.67% |
| 판단 전체 `decide` | 6.906초 | 100% |

**평가함수만 GPU로 옮겨도 개선 여지가 작다.** 위 비중이 유지된다면 평가 계산 시간이 0이 되어도 판단 전체 가속의 이론적 상한은 약 1.038배다. 실제 GPU 전송·호출 비용을 넣으면 더 작아진다. 전체 경기에는 엔진과 입출력도 있으므로 이 값을 경기 가속으로 해석하지 않는다.

이것은 고정 관측에 대한 단일 로컬 프로파일이다. 새로 생성한 명령이 이후 입력을 바꾸지 않으므로 승률 평가가 아니다. 계측 오버헤드와 공유 호스트 부하가 있으며, 다른 맵·전략에서는 비중이 바뀔 수 있다. [원시 기록](../records/compute/code-search-pilot/stages/result.json), [프로파일 도구](../experiments/profile_bot_stages.py)

읽기 검토로 찾은 다음 최적화 후보는 다음과 같다. 아직 적용·가속 검증한 변경은 아니다.

- 위험도 계산에서 매번 전체 칸을 훑는 반복을 맵별 근처 칸 목록과 실제 적 기수 위치 목록으로 줄인다.
- 같은 상태·진영의 거점 가치와 생산 단가를 호출 안에서 재사용한다.
- 탐색 첫 깊이에서 반복 생성하는 상대 행동 4개를 재사용한다. 완전한 4턴 탐색의 정책 호출 수는 116회에서 104회로 줄일 수 있지만, 실제 시간 감소는 별도 측정한다.

변경 후에는 출력·상태 전이 일치를 먼저 확인한다. 병력을 통째로 배정하는 변경은 순차 배정 결과를 바꿀 수 있으므로 단순 성능 최적화로 섞지 않는다.

## 2. 실제 경기의 CPU 병렬화

환경은 로컬 i9-13900H, 20논리 CPU, Python 3.14.7, GCC 16.2.1이다. 후보는 v2 그대로와 공학관 계수만 110→140으로 바꾼 예제이며, 팀원 봇을 상대한다. 맵 5000·5001 × Y/K × 후보 2개 = 같은 8작업을 실행 방식마다 반복했다. 측정 순서는 고정 난수로 섞었고, 각 설정을 한 번 실행했다.

| 방식 | 작업자 | 경기 실행 | 준비 포함 | 경기/초 | 후보 최대 응답 |
|---|---:|---:|---:|---:|---:|
| process | 1 | 28.09초 | 39.40초 | 0.285 | 49.1ms |
| process | 2 | 14.17초 | 25.78초 | 0.565 | 41.2ms |
| process | 4 | 8.41초 | 20.33초 | 0.952 | 50.9ms |
| process | 8 | 4.45초 | 15.74초 | 1.798 | 41.3ms |
| thread | 1 | 29.55초 | 41.15초 | 0.271 | 46.5ms |
| thread | 2 | 14.14초 | 25.66초 | 0.566 | 57.7ms |
| thread | 4 | 8.98초 | 21.31초 | 0.891 | 73.8ms |
| thread | 8 | 5.98초 | 17.74초 | 1.338 | 120.0ms |

관측상 가장 빠른 설정은 `process/8`이었다. 경기 실행 처리량은 `process/1` 대비 **6.31배**, 같은 작업자 수의 `thread/8` 대비 **1.34배**다. 준비까지 포함하면 `process/1` 대비 약 **2.50배**였다. 8개 설정 모두 경기 진행 해시가 동일하고, 오류·몰수는 0회였다. 두 후보는 각각 같은 4경기에서 4승이었다. 따라서 이 측정만으로 새 계수의 승률 우위를 주장할 수 없다.

경기 실행 시간은 프로세스 시작·엔진·봇·결과 기록을 포함하고 컴파일은 제외한다. 준비 포함 시간에는 매 실행의 소스 스냅샷과 컴파일도 들어간다. 두 후보 × 2개 맵의 짧은 파일럿이므로 큰 서버의 최적 작업자 수나 지속 처리량을 확정하지 않는다. 반복 실행을 새 독립 경기처럼 합산하지 않는다.

이 예제의 공학관 140은 도구 검증용 후보다. 새 최강 설정을 발견한 실험이 아니며, 추천 제출물은 기존 v2를 유지한다. [설정](../experiments/cpu_sweep_example.json), [전체 비교](../records/compute/code-search-pilot/executors/comparison.json)

## 3. GPU에 실제로 옮긴 범위

v2의 `evaluation`과 `building_value`를 CPU/CUDA 공통 계산으로 옮겼다. 공식 관측 488개에서 원본 C++ 평가함수와 대조하고, 공학관·추가 수입·병력 가치의 125개 조합을 처리한다. 관측 488개에는 각 경기의 마지막 상태도 포함한다. 판단 프로파일 483회와 다른 이유다.

원본 v2와 **488개 상태의 최대 오차 0**을 확인했다. 같은 공통 계산의 CPU 1·4스레드 결과도 일치했다. NaN·무한값·오차 초과는 실패 처리한다. NVRTC의 `compute_86` 커널 컴파일은 성공했다.

**실제 GPU 실행은 실패했다.** 로컬 RTX 4070 Laptop 환경에서 `cuInit`이 코드 100(`CUDA_ERROR_NO_DEVICE`)을 반환했다. `nvidia-smi`에도 온도·전력 등 일부 항목이 `ERR!`로 표시됐다. 원인을 확정하거나 드라이버를 변경하지 않았다. GPU 속도·CPU 대비 배속은 측정하지 않았으며, 이 결과로 3090 서버의 성능을 판단할 수 없다.

| 평가 호출 수 | 고유 상태·계수 조합 | CPU 1스레드 중앙값 | CPU 4스레드 중앙값 |
|---:|---:|---:|---:|
| 1,024 | 1,024 | 5.253ms | 1.864ms |
| 16,384 | 16,384 | 79.970ms | 22.330ms |
| 65,536 | 61,000 | 319.185ms | 82.734ms |

워밍업 2회 후 3회 측정했다. 위 CPU 시간은 준비된 입력의 공통 평가함수 호출만 포함하며, 관측 생성·컴파일·전체 대전은 제외한다. 상태 × 설정은 총 61,000개이므로 65,536호출 배치에는 반복 조합이 있다. [원시 측정](../records/compute/code-search-pilot/gpu-evaluation/result.json), [GPU 조회](../records/compute/code-search-pilot/nvidia-smi.log), [NVRTC 출처·해시](../records/compute/code-search-pilot/nvrtc-setup.json)

GPU 도구는 전체 경기나 행동 생성을 구현하지 않는다. 고정 상태의 이 계수들은 선형이므로 CPU에서도 불변 특징량을 캐시하면 더 줄일 수 있다. 현재 공통 커널의 반복 속도만으로 최적 튜닝 구조나 최강 설정을 결정할 수 없다. 계수를 바꾸면 실제 행동과 이후 경기 상태도 달라지므로 후보 선택에는 전체 대전이 필요하다.

GPU를 확대하려면 `후보 × 맵 × 상대 × 탐색 가지`의 큰 묶음을 처리하고, 가능하면 정책·전이·평가를 장치 안에 유지해야 한다. 현재 순차 배정과 분기가 많은 정책을 이식하는 비용부터 평가해야 한다. 평가함수만 옮기는 경로의 낮은 상한은 GPU 전체 경기 이식의 성능을 판정한 결과가 아니다.

## 4. 지금 실행할 수 있는 도구

후보별 설정, 소스·SDK·상대 스냅샷, 해시, 전체 결과, 오류, 턴 응답시간, 상세 리플레이를 저장한다. 완료 기록은 추가 저장하며 기존 실행 디렉터리를 덮어쓰지 않는다. `--resume`에서는 소스·설정·스냅샷 일치를 검사하고 완료 작업을 제외한다. 작업자 수는 바꿀 수 있다. 오류 기록은 자동 재실행하지 않으므로 원인을 해결한 뒤 새 실행으로 남긴다.

```bash
# 예제: CPU 전체 대전. 새 실행마다 다른 출력 경로 사용.
python3 experiments/cpu_sweep.py \
  --config experiments/cpu_sweep_example.json \
  --output-dir records/benchmarks/my-code-sweep-001 \
  --workers 8 --executor process --replays losses

# 중단한 동일 실행 재개
python3 experiments/cpu_sweep.py \
  --config experiments/cpu_sweep_example.json \
  --output-dir records/benchmarks/my-code-sweep-001 \
  --workers 8 --executor process --replays losses --resume

# 서버에서 병렬도 비교. 동일 작업 반복이며 승률 표본 증가가 아님.
python3 experiments/compare_cpu_executors.py \
  --config experiments/cpu_sweep_example.json \
  --output-dir records/compute/server-comparison-001 \
  --workers 1,2,4,8 --repeats 3
```

파라미터 생성기는 현재 `eng_bonus`, `income_bonus`, `army_weight`, `resource_weight` 네 계수와 v1·v2·팀원 상대를 지원한다. 실행 간 기준 소스가 바뀌면 새 실행을 만들어야 한다. 범용 임의 코드 생성이나 자동 irace 선택기를 구현한 것은 아니다.

CUDA가 정상 동작하는 서버에서는 [GPU 측정 도구](../experiments/gpu_probe/README.md)의 명령으로 1장부터 정확성·전송 포함 시간을 측정한다. NVRTC 라이브러리 경로는 서버 설치 위치로 바꾼다. 원격 3090 서버에는 접속하거나 실행하지 않았다.

## 5. 다음 후보를 고르는 순서

1. **패배와 연결된 변경을 만든다.** 공학관 경제 유지, 거점 수비, 종반 수비·경합을 서로 구분한 코드 후보로 만든다.
2. **CPU 큐에서 같은 맵·상대로 끝까지 대전한다.** 승패와 실패 리플레이를 비교해 유망한 후보를 확대한다. 경기 턴 수를 줄이면 이번 종반 패배를 놓치므로, 초기 예산은 맵 수로 조절한다.
3. **AI가 결과를 근거로 다음 코드를 수정한다.** 실행 중인 소스는 바꾸지 않고 새 버전으로 큐에 넣는다. 과거 강한 상대와 서로 다른 공략형을 남긴다.
4. **새 맵과 상대군에서 재검증한다.** Y 성적과 상대별 회귀, 몰수·응답시간을 확인해 최종 코드를 선택한다.
5. **GPU는 처리량 이득이 확인된 작업으로 확대한다.** 독립 배치를 1→2→4→8장에 분배하며 바로 전 규모와 비교한다. 실제 병목이 해소되는지 보고 배분한다.

현재 도구는 이 중 재현 가능한 대전 실행·기록·자원 비교를 구현했다. 자동 후보 승격, 여러 서버의 공용 큐, GPU 전체 경기 엔진, 새로운 강한 전략은 후속 구현 범위다. [검증 기록과 환경](../records/compute/code-search-pilot/README.md)
