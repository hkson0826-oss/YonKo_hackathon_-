# 다양한 코드 후보의 첫 대규모 리그

목표는 공식 패배를 겨냥한 구조 변경과 다른 알고리즘을 실제 경기로 비교하는 것이다. v2 기준선, 계수 조합 16개, 패배 개선 10개, 탐색 변경 10개, 독립 행동 생성기 6개로 **43개 후보**를 구성했다. 별도로 v1·팀원 봇을 고정 참조한다. 43개가 모두 독립 알고리즘이라는 뜻은 아니며, 같은 코드의 파라미터 대조군도 포함한다.

## 후보와 사전 약점

| 계열 | 비교할 가설 | 예상 약점 |
|---|---|---|
| 계수 16개 | ENG·추가 수입·병력·자원 가치 | 행동 후보에 없는 방어는 숫자만으로 만들 수 없음 |
| F/W 공동 수비 | 출발 병력을 예약해 동수 W 뒤의 F 경합을 유지 | 최악 위협을 여러 건물에서 중복 가정해 과잉 수비 |
| 공학관 유지·경제 평가 | 마지막 할인 거점의 보유와 생산 절약을 반영 | 중앙 점수 손실, 실제 생산 자원의 과대 추정 |
| 공동 도착·종반 평가 | F 목적지에 W를 함께 보내고 같은 예측 승패 안에서 점수 비교 | 다른 공격 병력 전용, 숨은 점수 추정 오차 |
| 탐색 10개 | 최악·평균·하위 평균, 깊이 1/2/4/6, 역할 전환, 국소 잔류 | 상대 모델 오류, 계산 시간, 정책 0 복귀 |
| 독립 경제·수비·집중 공격 | 다른 행동 생성기로 v2의 공통 맹점을 검사 | 기동·TELE·정찰 누락, 자원·위협 휴리스틱의 편향 |

각 후보의 구체적 설정·가설·약점은 생성기와 동결 manifest에 저장한다. 근거는 [공식 패배 분석](07-공식1차경기분석.md), [기존 연구](08-다양한접근과근거.md), [이번 Firecrawl 문헌 확인](../records/research/local-league-search/README.md)이다. 제한된 역할 전환·국소 후보를 논문의 완전한 RHEA·PGS 구현이라고 부르지 않는다.

## 게임 규칙과 구현 검사

전이 엔진은 배포 공식 Python 코드를 그대로 실행한다. 후보는 현재 참가자 관측만 받고, 리플레이의 숨은 실제 점수는 사후 분석에만 사용한다. 생산 위치·예산, 생산 직후 이동, 도착 유닛 재이동 금지, W 상쇄와 F 경합, 적 거점 2단계 점령을 검사했다.

검토에서 발견한 종반 보조 평가의 오류는 수정했다. 최종 0:28과 11:28이 모두 예측 패배일 때 11:28을 더 높게 보되, 승패·누적 점유·병력 동률 판정 순서는 유지한다. 실제로 이 변경이 승률을 올리는지는 별도 대전으로 판단한다.

로컬 통합 스모크 1경기(5901/Y)는 공동 수비 후보가 v2를 이겼고 오류·몰수 없이 완료했다. **한 경기의 승리는 우위 근거로 사용하지 않는다.** [기록](../records/league/local-smoke/result.json)

## 실행 전에 고정하는 비교 순서

| 단계 | 맵 | 구성 | 최대 경기 수 |
|---|---|---|---:|
| 실행 검사 | 5900 | 43후보 + v1·팀원 vs v2, 양 진영 | 90 |
| 넓은 선별 | 6000–6002 | 43후보 × 4상대 × 양 진영 | 1,032 |
| 후보 선택 | 6100–6107 | 다양성을 포함한 8후보 + v2 × 5상대 × 양 진영 | 720 |
| 미사용 맵 검증 | 6200–6223 | 사전 고정한 2후보 + v2 × 5상대 × 양 진영 | 720 |
| 상호 대전 | 6300–6301 | 상위 7후보 + v2의 모든 쌍, 양 진영 | 112 |

정상 후보가 충분하면 **2,674경기**다. 오류 후보는 실행 검사에서 제외하고 사유를 남긴다. 필수 상대가 실패하면 실행을 멈춰 환경·코드를 확인한다. 경기 자체는 끝까지 진행하며 초기 선별 예산은 맵 수로 조절한다.

주지표는 Y 승점률, 이후 최악 상대의 양 진영 승점률·전체 승점률·점수 차 순으로 비교한다. 선별의 6자리는 성적순으로 뽑되 같은 계열을 최대 2개로 제한하고, 2자리는 새로운 계열부터 채운다. 기존 v2는 모든 단계에 유지한다.

검증 전에 주 후보 1개와 보조 후보 1개를 고정한다. 주 후보의 Y 승점률 증가가 3%p 이상, 맵 단위 paired bootstrap 95% 구간 하한이 0 초과, 후보·기준선 모두 오류·몰수 0, 어느 상대에서도 Y 회귀가 10%p보다 크지 않을 때 내부 승격 대상으로 삼는다. 그렇지 않으면 v2 추천을 유지한다. 상대군이 실제 참가자 분포와 같다는 보장은 없다. 보조 후보의 검증 결과를 보고 새 주 후보로 바꾸면 새로운 검증 맵을 사용한다.

상호 대전은 양쪽 관점을 함께 집계하고 원 경기 수는 한 번만 센다. 같은 맵의 상대·진영을 독립 맵처럼 취급하지 않는다.

## TMP 실행과 원상복구

로컬 스모크 뒤 사용자가 `ssh yonsei-root` CPU 서버를 허용했다. 확인한 접근 범위는 52논리 CPU, 약 440GiB RAM이며 기존 부하는 낮았다. **원격 작업은 항상 `/tmp/yk-league-*` 안에서 진행한다.** 필요한 파일만 전송하며 `.git`, 접속 정보, 로컬 운영 파일은 보내지 않는다.

- CPU affinity는 최대 46/52(88.5%), 실제 경기 worker는 우선 16개로 제한한다. 프로세스는 낮은 우선순위(`nice +5`)로 실행한다.
- 프로세스당 주소공간 768MiB, worker·봇·셸을 포함한 보수적 예상 합계 약 66GiB다. 실행 시 사용 가능 RAM의 90% 이내인지 검사한다. 시스템 가용 RAM이 전체의 10% 아래로 내려가면 중단한다.
- 필요한 Python·g++가 이미 있어 추가 패키지를 설치하지 않는다. 향후 설치가 필요하면 TMP 가상환경·별도 경로에 설치하고 제거로 원상복구한다.
- 결과를 로컬에서 SHA-256 검증·압축 해제한 뒤 ACK를 보내고 원격 TMP 삭제 확인을 받는다. 종료·오류·연결 종료·시간 제한 경로에서 자식 프로세스도 정리한다.
- SIGKILL·서버 장애는 정상 정리 경로를 막을 수 있으므로 마지막 삭제 확인이 없으면 복구 완료라고 보고하지 않는다. 사용자의 시스템 로그나 기존 프로세스를 지우는 작업은 하지 않는다.

```bash
python3 experiments/run_remote_tmp.py \
  --host yonsei-root \
  --output-dir records/league/campaign-001 \
  --command python3 experiments/league_campaign.py --arena output --workers 16
```

모든 경기의 결과·응답시간·공학관 할인 턴·실제 생산·사망·점수 급락을 기록한다. 패배·무승부와 각 단계 첫 맵의 대표 승리는 전체 리플레이를 gzip으로 저장한다. 실행 중 코드를 바꾸지 않는다. 실행 코드·설정은 먼저 `jisang`에 커밋·푸시하고, 완료 단계와 최종 분석도 같은 브랜치에 보존한다. 실제 제출물 교체·업로드는 별도 검증 후의 작업이다.
