2026-09-28. **잠금 주 후보 `a_v2_terminal_local`이 새 맵 Y 269/320승, v2가 185/320승**이었다. 차이는 **+26.25%p**, 맵 단위 bootstrap 95% 구간은 **+18.13~+34.38%p**다. 사전 승격 조건·교차 계열 추가 감사·실제 ZIP 실행 검사를 통과해 **[submission-v3.zip](../artifacts/submission-v3.zip)을 추천**한다. ## 실제로 수행한 개선 루프

신규 소스는 **24개 첫 후보 + 12개 재수정 = 36개**다. 기준선·고정 상대는 별도로 유지했다. 기존 후보 소스 해시는 재수정 때도 보존했다.

| 반복 | 코드·판단 | 완료 경기 |
|---|---|---:|
| 1차 | v2 원인 분리 8개, 공동 임무 배정 8개, 행동 탐색 8개를 반례·컴파일·합법 명령 검사 후 비교 | 2,058 |
| 재수정 | 첫 패배를 읽고 방어·종반 행동·초반 지연·F 상한·경유점 호위·역할 유지 등 12개 새 소스 생성 | 코드·반례 검사 |
| 2차 | 기존 대조 9개 + 재수정 12개 + v2. 개발→독립 선택→잠금 주 후보의 미사용 맵 검증→상호 대전 | 4,892 |
| 추가 감사 | 최초 잠금 주 후보와 v2를 새 알고리즘 계열 6종·32개 새 맵에서 비교, 384MiB 주소공간 적용 | 768 |

두 번의 완료 리그는 **6,950경기**, 오류·몰수 0이다. 첫 반복은 7000–7007, 두 번째 개발은 7100–7107, 선택은 7200–7215, 최종 검증은 7300–7363이다. 수정에 사용한 맵을 미사용 검증으로 재사용하지 않았다. [첫 결과](../records/league/loop2-iteration1/README.md), [두 번째 전체 결과](../records/league/loop2-iteration2/README.md).

추가 감사 7500–7531까지 포함하면 **서로 다른 132개 맵에서 총 7,718경기**, 모두 완료했고 오류·몰수는 0이다. 서로 다른 맵 수와 동일 맵의 상대·진영별 경기 수를 구분한다.

새 수정이 전부 좋아지지는 않았다. 같은 2차 개발 Y40경기에서:

- 좁은 위협 창은 9승, 즉시 F/W 방어를 더한 수정은 32승이었다. 첫 반복의 좁은 창 30승만 보고 채택했으면 새 맵 회귀를 놓쳤다.
- 역할 혼합을 미래 전개에도 유지한 수정은 부모 25승에서 13승으로 악화돼 탈락했다.
- 공동 배정의 초반 적용 지연은 부모 33승에서 29승, F 상한 수정은 28승에서 27승이었다. 더 복잡한 변경을 자동 채택하지 않았다.
- 상대 적합도·병종별 이동 후보는 개발 37승으로 1위였지만 독립 선택에서 58/80승으로 밀렸다.

[수정 전후 대응 비교](../records/league/loop2-iteration2/revision-effects.md)는 같은 맵·상대의 부모 후보와 비교한다. 작은 개발 집합의 탐색 결과이며 다중 비교 편향을 보정한 최종 증거는 아니다.

## 선택한 알고리즘과 한계

기존 네 정책이 만든 전체 명령을 출발점으로, 중요한 출발지 최대 세 곳에서 다른 정책의 명령과 스크립트 밖 인접 이동을 비교한다. 상대 네 정책과 최대 3턴을 시뮬레이션하고 평균 75%·최악 25%로 평가한다. 완전히 평가한 최선 행동만 보존한다. 종반에는 기존 승패 평가 등급을 유지하면서 점수차를 작은 추가 기준으로 쓴다.

[행동 추상화 연구의 원문 확인](../records/league/loop2-design/adaptive-search-sources.json)을 이 게임에 제한해 적용했다. 신경망·오프라인 학습 가중치 없이 제출 가능한 C++ 코드다. 전역 최적 PGS/RHEA나 균형 전략을 증명한 구현은 아니다.

여전히 세 출발지·3턴·네 상대 정책이라는 제한이 있고, 자유 이동은 F/W 전량을 함께 보내는 방식이라 병종별 대기·부분 분할을 놓칠 수 있다. 135ms는 협력적 탐색 중단 예산이며 한 정책·전이를 강제 선점하지 않는다. 실제 주 후보의 최종 검증 최대 응답은 117.16ms, 추가 감사는 114.18ms, ZIP CPU 검사는 136.58ms였다. 공식 CPU/GCC 12.2에서의 보장은 아니다.

[남은 패배도 검사했다](../records/league/loop2-design/final-primary-loss.md). 7338/Y 팀원전은 새 후보 9:32 패, v2 22:19 승이었다. 두 경기 320개 전이를 재현했고, 121턴 실제 상대 명령을 고정한 채 우리 F 이동 한 줄만 제거하면 2점을 보존할 수 있었다. 그 행동으로 전체 경기를 이긴다는 증명은 아니다. 현재 소스·채택 기준에 즉석 수정은 섞지 않았으며, 이 사례를 활용할 다음 버전은 새 맵에서 검증해야 한다.

## 최종 제출 ZIP 검사

최종 검증·추가 감사의 선택 lock과 소스 해시를 대조한 뒤, 고정 소스 네 파일만 ZIP에 넣었다. **12,207바이트**, SHA-256은 `ce94e80a49d833be8b3c093a34319d8b9cdb5b7ec8d86b91a4b2831b18d799cb`다. ZIP에서 다시 꺼낸 실제 소스로 컴파일했다.

- SDK 형식 검사와 실행 1경기: 문제·출력 경고 없음.
- v2 상대 새 맵 7550·7551 양 진영 4경기: 오류·몰수 없음. 승률 승격용 표본이 아닌 실행 회귀 검사다.
- 300ms/턴·첫 턴 3,000ms, 프로세스별 384MiB 주소공간·180초 제한 적용. 후보 최대 응답 136.58ms.
- 로컬 컴파일러는 GCC 16.2.1/C++20. 공식 GCC 12.2.0 컨테이너 검증은 아직 하지 않았다.

검사 결과·출력량·전체 리플레이는 [records/submissions/v3](../records/submissions/v3/README.md)에 있다. 여기의 5경기는 후보 리그 7,718경기와 별도다. 로컬 파일명 v3는 업로드 후 사이트 버전 번호를 뜻하지 않는다. 기존 공식 1차에 쓴 파일은 로컬 v2이며, 새 ZIP은 아직 업로드하지 않았다.

## 기록과 공용 서버

모든 승리·패배의 리플레이, 단계별 결과, 동결 소스·SDK·상대 해시, 실행 명령·환경·오류를 보존한다. 7,718개 전체 리플레이의 해시·출력량과 원본 보존을 확인했다. 공용 서버는 CPU affinity 46/52개(88.46%)·16 worker, 보수적인 메모리 상한으로 TMP 안에서 실행했다. 패키지·시스템 설정은 바꾸지 않았다. 세 원격 실행 모두 결과를 회수한 뒤 TMP를 삭제했고, 각 경로와 관련 프로세스가 없음을 독립 확인했다. [첫 반복](../records/league/loop2-iteration1/artifact-verification.json), [두 번째 반복](../records/league/loop2-iteration2/artifact-verification.json), [추가 감사](../records/league/loop2-cross-family/artifact-verification.json)에 증거를 남겼다. 로컬 ZIP 빌드·실행 TMP도 정리했다.

전체 작업과 기록은 `jisang`에 단계별 커밋·푸시했다. 기존 공식 JSON 5개와 v2 ZIP은 그대로 보존하며 `main`은 변경하지 않았다. 실제 업로드와 대회 사용 코드 선택은 사용자가 한다.
