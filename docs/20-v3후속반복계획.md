# v3 이후 개선과 상대군 강화

2026-09-28 KST. 제출 마감은 사용자 확인에 따라 **오늘 오전 8시**다. 현재 추천 [submission-v3.zip](../artifacts/submission-v3.zip)은 그대로 보존한다. 새 후보가 사전 검증·실제 ZIP 검사를 통과하기 전에는 추천을 바꾸지 않는다. 업로드·사이트 제출 선택은 사용자가 한다.

## 출발점과 연구

v3는 기존 정책 밖 인접 이동을 비교하면서 v2보다 강해졌다. 그러나 종반 보정 자체의 추가 효과는 불확실했고, 3개 출발지·3턴·4개 상대 정책이라는 제한과 병종별 정지·분할 누락이 남았다. [이전 결과](19-반복개선검증결과.md)와 원본 소스를 기준선으로 동결한다. 기존 holdout에서 읽은 사례는 이제 개발 근거이며 새 검증에 재사용하지 않는다.

세 작업을 병렬로 진행한다. 각 후보는 연구나 실제 패배와 연결된 가설, 적용 조건, 약점, 규칙 반례 검사를 가져야 한다.

| 계열 | 확인할 문제와 접근 |
|---|---|
| 실패 수리 `f3_` | 경제 거점 상실·생산 격차·안전한 점령 누락을 공식 엔진 전이와 대체 행동으로 확인 |
| 행동 공간 `s3_` | F/W 독립 대기·부분 분할·두 출발지 공동 변경·beam·선별 평가 등 후보 생성 구조 비교 |
| 상대 대응 `r3_` | 상대 행동 다양화·국소 적대 대응·위험 평가·regret 기반 선택을 제한 시간 안에서 비교 |

Firecrawl 논문 인덱스에서 원문과 관련 방법을 확인하고, 논문의 게임·관측·행동·계산 예산이 이 대회와 다른 점을 기록한다. 논문의 일반적인 강점을 이 게임의 실측 승리로 간주하지 않는다. 소스와 자료는 [loop3-design](../records/league/loop3-design/)에 둔다.

## 상대도 함께 강화하는 순서

고정 상대 여섯 종은 `v3`, `v2`, 팀원 Python 봇, `a_v2_tactical_local`, `j_balanced_portfolio`, `j_v2_reclaim_relay`다. 과거보다 강한 v3와 서로 다른 탐색·공동 배정·호위 접근을 포함한다. 소스 구조가 공유되는 상대가 많다는 한계는 유지된다.

1. 첫 반복: 신규 후보와 v3를 고정 상대군·8100–8107 새 맵의 양 진영에서 비교한다. 8099는 실행 검사다.
2. 개발 기록에서 v3 직접 상대 점수가 높은 후보 두 개를 다른 생성기 계열에서 뽑는다. 양 진영 점수율, 평균 점수차, ID 순으로 결정한다. 오류·몰수가 있는 후보는 제외한다. 소스 SHA와 선택 근거를 고정한다.
3. 각 계열의 실패·회귀를 읽고 실제 코드를 수정한다. 기존 후보는 덮어쓰지 않는다. 새 수정과 남긴 대조 후보를 8200–8207에서 다시 비교한다. 이때 고정 여섯 종에 위 공략형 두 종을 추가한다.
4. 최대 여섯 후보와 v3를 8300–8323에서 선택한다. 첫 주 후보와 두 번째 후보를 잠근 뒤 8400–8479에서 최종 검증한다. 최종 결과를 보고 주 후보를 바꾸지 않는다.
5. 8600·8601의 상호 대전은 상성 진단이다. 별도 승격 근거로 선택 실패를 뒤집지 않는다.
6. 주 후보가 위 최종 검증을 통과한 경우에만 8700–8731에서 같은 여덟 상대의 추가 감사를 진행한다. 전체·고정군·추가군의 Y 평균 회귀 없음, 상대별 Y 회귀 12.5%p 이내, 누락·중복·오류·몰수 0을 요구한다. 통과 후 ZIP 실행 검사는 8800·8801의 양 진영 네 경기로 수행한다.

상대가 바뀌어 승률의 분모가 달라지는 문제를 막기 위해 **고정 상대군과 추가 공략형 상대군의 결과를 따로** 보고한다. 공략형 선택은 개발에만 의존한다. 강한 신규 상대라고 부를 때에는 v3와 실제 대전한 결과를 함께 제시하며, 승리 근거가 약하면 그 한계를 명시한다.

## 사전 승격 조건

우리 진영 Y를 주목표로 삼되 K 회귀도 제한한다. 무승부는 0.5점이다. 기준선은 v2가 아닌 현재 v3다.

- 같은 맵·상대·진영의 계획 경기 전부 완료, 중복·누락 없음, 후보·v3 오류와 몰수 0.
- 전체 Y 개선 **3%p 이상**, 맵 단위 paired bootstrap 95% 구간 하한이 0 초과.
- 고정 여섯 상대만으로도 Y 개선 **3%p 이상**, 같은 구간 하한이 0 초과.
- 추가 공략형 상대군의 Y 평균 회귀 없음. 각 상대의 Y 회귀는 10%p 이내.
- 전체 K 회귀는 5%p 이내. v3 직접 상대 양 진영 점수율은 50% 이상.
- 최초 잠금 주 후보만 승격 가능. 실전 컨테이너와의 차이를 표시하고, 실제 ZIP에서 재컴파일·출력·시간·메모리 검사를 통과해야 추천 변경.

이 기준이 실패하면 v3를 유지한다. 임의의 10점이나 전승 보장은 선언하지 않는다. 후보 소스를 검증 후 수정하면 새 버전이며 새 맵 검증이 필요하다.

## 자원·기록·마감

공용 서버 `yonsei-root`의 모든 실행은 전용 TMP에서 한다. CPU affinity는 사용 가능 코어의 90% 이하, worker 16개이며 기존 부하에 따라 줄인다. 메모리 여유 10%를 지키고, 컴파일 이후 경기 worker와 봇은 프로세스별 384MiB 주소공간 제한을 상속한다. 공식 300ms 턴 제한을 늘리지 않는다. 패키지·설정을 바꾸지 않고, 회수 후 TMP와 관련 프로세스가 없음을 확인한다.

승패와 관계없이 전 경기 리플레이, 소스·상대·SDK 해시, 환경·응답 시간·오류를 저장한다. 실행 전 동결과 각 완료 단계는 `jisang`에 커밋·푸시한다. 이후 사용자가 대량 실험 전 `main` 공유를 요청해 검증된 v3 제출물·최종 소스·요약 25개 파일만 `e73b402`에 선별 게시했다. [게시 범위·해시·TMP 정리](../records/submissions/v3/main-share.json)에 기록했고 개발 브랜치는 계속 `jisang`이다.

목표는 오전 6시 전후에 최종 검증을 마치고 제출 검사·업로드 여유를 확보하는 것이다. 오전 7시 15분 이후에는 검증 시간이 불확실한 새 후보 실험을 시작하지 않는다. 마감이 가까워져도 미완료 실험을 통과로 간주하지 않는다.
