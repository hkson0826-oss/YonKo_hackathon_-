# v3 후속 검증 결과

2026-09-28 KST. **현재 제출 추천은 기존 v3다.** 두 차례 리그와 추가 32맵 검증을 마쳤지만 주후보가 추가 검증의 고정군·상대별 회귀 조건에 실패했다. 이 실행에서 새 ZIP을 만들지 않았다. 두 리그와 추가 검증의 원본 해시·출력 제한·원격 정리를 모두 확인했다.

사전에 잠근 주후보 `f3_v2_warrior_reserve`는 새 80맵 holdout에서 v3 대비 Y 승률이 **+5.47%p** 높았다. 내부 승격 조건은 통과했지만, 아래 수치를 리더보드 보정 점수나 대회 우승 확률로 해석하지 않는다.

## 공식 패배에서 실제 코드 수정까지

공식 1차의 로컬 제출물은 v2다. 사이트에서 표시된 당시 v3와 현재 로컬 v3를 구분한다. 패배 경기에서는 W 생산이 698:758, 공학관 할인 적용이 72:117턴이었고 전투 손실은 양쪽 모두 637명이었다. 종반에는 F가 죽지 않아도 점령을 잃었다. 경제·호위·위치 문제를 조사할 근거이며, 하나의 원인으로 전체 패배를 확정한 것은 아니다. [공식 경기 분석](https://github.com/hkson0826-oss/YonKo_hackathon_-/blob/2daae2c89434bbdd0a14f20f0e0fe070e60b36e0/docs/07-공식1차경기분석.md)

이후 v3의 실제 패배를 재생하니 7338/121턴에는 F 대기 후보가 이미 있었다. 3턴 평가가 이탈을 선호했고, 다음 두 턴까지 F를 고정해도 적 W에 사망하는 반례 때문에 순위가 뒤집히지 않았다. “대기만 추가하면 해결”이라는 설명을 기각하고 현재 행동·호위·후속 정책을 나눠 수정했다. [결정·후속 정책 진단](https://github.com/hkson0826-oss/YonKo_hackathon_-/blob/2daae2c89434bbdd0a14f20f0e0fe070e60b36e0/records/league/loop3-design/evidence-summary.md)

임무 배정·평가, 행동 공간·선별 탐색, 상대 모델·위험 평가의 세 계열에서 **새 후보 21개**를 구현했다. 첫 대전의 성공·실패를 읽고 **12개를 새 ID로 실제 재수정**했다. 총 33개이며 기존 후보 소스와 상대는 보존했다. 연구 적용은 PGS·비대칭 행동 추상화·공동 행동 평가·여러 상대 집단 등의 원리를 이 게임의 관측과 CPU 제한에 맞춘 것이다. [연구와 적용 한계](https://github.com/hkson0826-oss/YonKo_hackathon_-/blob/2daae2c89434bbdd0a14f20f0e0fe070e60b36e0/records/league/loop3-design/evidence-summary.md#4-연구-접근의-채택보류-이유)

## 주후보가 바꾼 것

`f3_v2_warrior_reserve`는 **현재 턴의 위험한 보유 거점에 W를 남기는 선택지**를 원래 네 정책에 추가한다. 기존 선택지는 남기고, v3의 평가 함수·상대 정책·공식 전이를 유지한다. 다음 예상 턴은 원래 continuation 정책으로 평가하며 실제 다음 턴에는 새 관측으로 다시 탐색한다.

W 잔류를 매턴 강제하거나 상대 정책까지 같은 방식으로 고치는 후보가 아니다. 추가 선택지가 탐색 시작점을 바꾸면 이후 국소 탐색의 최종 F/W 이동도 달라질 수 있다. 실제 개선 사례에는 첫 분기에서 W 잔류 증가 없이 여러 이동이 달라진 경우도 있었다. 따라서 성능 차이 전체를 “남긴 W 덕분”으로 단정하지 않는다. [현재 턴 수리의 범위와 승리·회귀 증거](https://github.com/hkson0826-oss/YonKo_hackathon_-/blob/2daae2c89434bbdd0a14f20f0e0fe070e60b36e0/records/league/loop3-design/warrior-reserve-development-audit.md)

## 완료한 실험 범위

1차 **2,166경기·9개 맵**, 2차 **9,198경기·115개 맵**으로 합계 **11,364경기·124개 서로 다른 맵**을 확인했다. 실행 검사·개발·선택·holdout·교차 대전을 포함한 수이며, 한 단계의 독립 검증 표본 수로 합쳐 세지 않는다. 두 리그의 기록상 오류·몰수는 0이다.

고정 상대는 v3·v2·팀원 봇·기존 강한 후보 등 6종이다. 첫 개발 자료에서 v3를 양 진영 합계 각각 10/16회 이긴 `s3_selective_contact`, `r3_opponent_league`를 새 공략형 상대 2종으로 고정했다. 개발 결과로 고른 상대이므로, 원래 상대와 추가 상대의 성적을 분리한다.

개발 8맵과 선택 24맵 이후 주후보를 잠그고, 별도 80맵에서 후보별 **Y 640경기·K 640경기**를 평가했다. 같은 맵 양 진영·상대·소스·실행 제한을 고정했다. [계획과 잠금 기록](https://github.com/hkson0826-oss/YonKo_hackathon_-/blob/2daae2c89434bbdd0a14f20f0e0fe070e60b36e0/records/league/loop3-iteration2/locked-finalists.json)

## Holdout 결과

무승부는 없었다. 괄호 안 Y 차이는 v3 대비 %p이며, 고정군은 진영별 480경기, 추가군은 160경기다.

| 후보 | 전체 Y 승수 / 640 | 전체 K 승수 / 640 | 고정군 Y 승수 / 480 | 추가군 Y 승수 / 160 |
|---|---:|---:|---:|---:|
| v3 | 373 | 415 | 293 | 80 |
| 사전 주후보 `f3_v2_warrior_reserve` | **408 (+5.47)** | 411 | 321 (+5.83) | 87 (+4.38) |
| 후순위 `s3_v2_screen_paired_guard` | **424 (+7.97)** | **450** | 335 (+8.75) | 89 (+5.63) |

주후보의 Y 차이 95% 구간은 **+0.78~+10.16%p**다. 고정군은 +0.83~+10.83%p, 추가군은 -3.75~+12.50%p로 추가 상대만의 개선은 확정하기 어렵다. K는 415승→411승, **-0.625%p**였다. 구간은 같은 맵의 경기를 묶은 5,000회 bootstrap이며 실제 미지 참가자나 보정 점수에 대한 구간이 아니다.

후순위 s3는 이 holdout에서 더 높은 성적을 냈다. holdout을 보기 전에 **첫 주후보만 승격 가능**하도록 잠갔으므로 이 표를 보고 후보를 교체하지 않는다. s3는 다음 연구의 유력한 출발점이며, 이를 주후보로 다시 검증하려면 새 사전 계획과 독립 맵이 필요하다. [전체 단계별 결과](https://github.com/hkson0826-oss/YonKo_hackathon_-/blob/2daae2c89434bbdd0a14f20f0e0fe070e60b36e0/records/league/loop3-iteration2/README.md)

## 수정한 12개가 모두 개선된 것은 아니다

부모와 같은 개발 경기끼리 비교하면 `soft_matching`은 Y -14.1%p, `tail_recheck`는 Y -21.9%p였다. 대부분의 수정은 부모 대비 이득이 확정되지 않았고, 일부는 실제 회귀했다. 내부 평가를 완화하거나 검사를 더 붙였다는 이유만으로 강해졌다고 판단하지 않는다. [12개 수정의 부모별 비교와 불확실성](https://github.com/hkson0826-oss/YonKo_hackathon_-/blob/2daae2c89434bbdd0a14f20f0e0fe070e60b36e0/records/league/loop3-iteration2/revision-comparison.md)

성공 사례의 내부 이득 +1.17보다 실패 사례의 +5.65가 컸으므로 단순 최소 이득 문턱도 기각했다. 상대별로 같은 기준 행동과 비교하는 검사를 구현했지만, 이 검사 역시 실제 리그에서 판단했다. 기본 탐색 시간 변경의 별도 감사에서는 일부 원격 행동을 로컬에서 재현하지 못해 원인을 미확정으로 남겼다. [s3 수정 근거](https://github.com/hkson0826-oss/YonKo_hackathon_-/blob/2daae2c89434bbdd0a14f20f0e0fe070e60b36e0/records/league/loop3-design/action-search-iteration2.md) · [시간 예산 감사](https://github.com/hkson0826-oss/YonKo_hackathon_-/blob/2daae2c89434bbdd0a14f20f0e0fe070e60b36e0/records/league/loop3-design/intact-base-development-audit.md)

## 추가 32맵에서 승격 보류

새 맵 8700–8731에서 v3와 주후보를 같은 8상대·양 진영에 붙인 **1,024경기**를 완료했다. Y 전체는 v3 160/256승→후보162/256승, K는165→178승이었다. 하지만 고정 6상대 Y는2승 감소(-1.04%p), `j_v2_reclaim_relay` 상대 Y는8/32승 감소(-25%p)했다. 고정군 Y 비회귀와 상대별 회귀≤12.5%p 두 조건에 실패했다. 앞선 80맵의 이득으로 이 실패를 덮지 않는다.

두 리그와 추가 검증의 합계는 **12,388경기·156개 서로 다른 맵**, 오류·몰수0이다. 각 경기 리플레이 해시와 출력 제한을 검사했고, 공식 원본5개·v2/v3 ZIP 보존과 두 원격 TMP의 폴더·프로세스 정리도 독립 확인했다. 리그의 384MiB 주소공간·300ms 제한은 공식 서버 컨테이너와 동일한 환경 인증이 아니다.

이 실행의 추천은 v3 유지다. 다음에는 고정한 `s3_v2_screen_paired_guard`를 별도 실험으로 검증한다. 지금까지 본 맵은 개발 자료로 취급하고 새 128맵 확인·48맵 추가 검증을 한 번만 진행한다. 실패한 f3나 후순위를 이 실행의 승자로 바꿔 기록하지 않는다. 새 검증도 실패하면 추가 재시도 없이 v3를 유지한다. 새 제출물의 생성은 별도 검증 통과 후이며, 업로드와 제출 선택은 사용자가 담당한다.
