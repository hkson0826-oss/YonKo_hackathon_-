# 최신 규칙과 독립 임무 봇 — 2026-10-01

이번 목표는 기존 v8의 네 정책·짧은 탐색·후처리 방어를 다시 조합하는 대신, **목표 도착과 F/W 호위를 함께 배정하는 별도 봇 한 개**를 만드는 것이다. 먼저 기존 연구, 최신 공지, 최근 공식 패배를 다시 읽었다. 약한 팀원 v1 상대 승률을 주요 평가로 쓰지 않는다. 이 문서는 사전 연구·실험 계획이며 성능 결과는 별도 기록한다.

## 확인 범위와 규칙 정정

- 기존 전략·결과 docs/02·03·08·12·16~29와 다섯 연구 묶음, 관련 구현을 대조했다. 전체 문서·연구 파일 98개의 목록과 해시를 남겼다. 모든 raw 문헌 발췌를 전부 재독했다는 뜻은 아니다. [기존 연구 검토](../records/research/new-bot-20261001/prior-research.md).
- 공식 규칙서·SDK·전이·맵·러너를 확인하고 기존 18개 및 새 24개 반례를 통과했다. [규칙 감사](../records/research/new-bot-20261001/rules-audit.md).
- 로그인한 Chrome에서 공지 11개와 규칙·개발·운영 안내 전체를 펼쳐 읽었다. [공식 사이트 확인 기록](../records/research/new-bot-20261001/site-review.json), [공지 원문](https://yonsei-vs-korea-hackathon.kr/announcements), [규칙 원문](https://yonsei-vs-korea-hackathon.kr/rules).
- 9/28 FAQ는 **값을 정한 방법을 제한하지 않고 소스·헤더의 상수·배열을 허용**한다. 별도 데이터·가중치·실행파일 제출과 런타임 외부 파일/네트워크는 금지다. 과거 문구를 학습된 소스 상수까지 모두 금지한다고 해석하면 틀린다. 규칙 기반 봇은 이번 구현·검증에 맞춘 선택이다.
- 최종 업로드는 **10/1 23:00**, 선택·보고서는 **23:59**다. 15:00은 마지막 참고 리더보드 반영, 17:00은 공개 시점이다. 이전의 20:00 일일 기준과 구분한다. 업로드와 선택은 별도다.
- 타 참가팀 코드 교환·별도 다팀 대전 시스템 금지 공지를 확인했다. 이번 분석은 공식 리플레이, 동일 팀의 기존 후보와 공개 일반 연구를 쓴다. 타 참가팀 코드를 취득하거나 실행하지 않았다.
- 일반 턴 300ms / 첫 턴 3000ms, 메모리 384MiB, 경기 인프라 180초, C++20/GCC12.2, ZIP 5MiB·해제 20MiB·200파일 제한을 다시 확인했다.

## 새로 만드는 구조와 선택 이유

논문 3개와 다른 대회인 Lux 우승자의 공개 회고를 원문으로 다시 확인했다. 온라인 임무 재배정, 제한된 시간창, 지속 역할·중복예약 해제를 참고한다. MAPF의 아군충돌금지, 초단위 솔버 성능, 정확한 최적반응의 이론 보장을 이 게임에 그대로 적용하지 않는다. 이번 참가팀의 검증 가능한 최신 공개 전략글은 검색에서 찾지 못했다. [외부 연구와 출처](../records/research/new-bot-20261001/external-research.md).

| 구분 | v8 | 새 임무 후보 |
|---|---|---|
| 결정의 중심 | 고정 정책 4개·짧은 모의 전이·국소 이동 수정·후처리 방어 | 목표·예상 도착·F·현재 W 호위·생산비를 가진 임무 묶음 |
| 생산·호위 | 정책별 생산 후 F/W 이동, 추가 방어 | 후보에 F 생산 위치와 W 증원비를 포함하고 공통 장부 사용 |
| 지속성 | 기존 결정 코어의 임무 기억 없음 | 예상 다음 셀과 관측 F 수를 맞춰 지속·취소 |
| 탐색 | 정책 후보와 국소 행동 rollout | F 공동 배정 폭 12 beam, 6턴 경로 위험·ETA 근사 |
| 안전성 | 모델 혼합 평가·ETA 방어 | 정지 적·당턴 도착 위협과 현재 호위량 검사 |
| 종반 | 기존 평가와 방어 | 이번 턴 중립화·탈취가 바꾸는 현재 점수 반영 |

이 후보도 미래 6턴의 병력·자원을 모두 보장한 최적 스케줄러는 아니다. 방어와 남은 W 배정은 탐욕 방식이고, 셀별 적 도착 상한은 서로 배타적인 위협을 중복 수비할 수 있다. 설계와 구현의 차이를 [DESIGN](../experiments/mission_scheduler_20261001/DESIGN.md)에 명시한다.

초반에는 도착 ETA·경제가치로 확장하되 지나친 안전성으로 지연될 위험이 있다. 정찰은 적 위치가 이미 공개이므로 숨은 점수가 목표를 바꾸는 가치와 비용을 비교해야 하며 첫 구현은 S를 생산하지 않는다. 방어는 적 F 도착 기한과 증원을 연계하지만 선예약이 공격기회를 줄일 수 있다. 이 세부 장단점은 실전 결과로 판정한다.

## 사전 실험 계획

[고정 계획](../records/research/new-bot-20261001/experiment-plan.json)을 먼저 저장한다. 소스·테스트·해시를 커밋·푸시한 뒤 별도 arena에 복사해 실행한다. 실행 중인 스냅샷은 수정하지 않는다.

1. 규칙 42개와 새 봇 프로토콜 9개, 공식 실패 관측을 통과시킨다. 실제 SDK로 초과 생산·이동·TELE·종반 점유를 검사한다.
2. 개발용 19000–19003의 4맵 양 진영에서 v8 직접전 8경기를 진행한다. 강한 공통 상대 시험은 19010–19013에서 후보와 v8을 각각 s3_selective_contact, r3_opponent_league, j_balanced_portfolio와 대전시킨다. 총 48경기다.
3. 크게 무너지면 경기의 첫 실패, F 손실, 경제 획득, 정체를 읽고 같은 임무 계열을 수정한다. 새 소스·실행 ID를 만들고 기존 결과를 보존한다. 후보 수를 늘리기 전에 원인을 확인한다.
4. 유망하면 선택용 19100–19107과 최종 검증용 19200–19207을 분리한다. 최종 맵을 읽고 수정하면 개발 집합으로 옮기고 새 최종 맵을 쓴다. 약한 팀원 v1은 주평가에서 제외한다.
5. 평균뿐 아니라 Y/K·상대별 승무패, 최종 점수, F 생산·손실, 정체, 응답 분포, 오류·몰수를 남긴다. 모든 경기의 행동을 감사하고 원본 리플레이를 보존한다. 우위가 불분명하면 새 임무 봇으로 서버 선택을 변경하지 않는다. v8은 이번 고정 비교 기준선이다.
6. 새 후보는 결과에 맞게 검증용 ZIP으로 보존한다. 제출 가능성은 실제 ZIP의 GCC12 빌드·SDK·384MiB 실행으로 별도 검사하며 후보 완성과 서버 선택 변경을 구분한다.

현재 서버 선택 v9는 변경하지 않는다. 새로운 구조라는 사실과 더 강하다는 주장은 별개이며, 강한 고정 상대·새 맵 결과가 나와야 후자를 판단할 수 있다.
